## Spring Core – IoC

Since you already know React, think of **Spring IoC as a framework-managed dependency system**.

### 1. What is IoC?

**IoC = Inversion of Control**

Normally, your class creates the objects it needs:

```java
class OrderService {
    private PaymentService paymentService = new PaymentService();
}
```

Here, `OrderService` controls the creation of `PaymentService`.

With Spring:

```java
class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Spring creates `PaymentService` and gives it to `OrderService`.

So:

> **Instead of your code creating dependencies, Spring creates and manages them.**

This is **IoC**.

---

# 2. Dependency Injection

**DI = Dependency Injection**

A dependency is simply an object that another object needs.

```text
OrderService
     |
     | needs
     ↓
PaymentService
```

Spring injects `PaymentService` into `OrderService`.

### Constructor Injection — recommended

```java
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Spring sees:

```text
OrderService → requires PaymentService
                     ↓
                 Spring creates it
                     ↓
              injects into OrderService
```

### Why constructor injection?

* Dependency is explicit.
* `final` can be used.
* Object cannot exist without required dependency.
* Easier unit testing.
* Preferred approach in Spring applications.

---

# 3. What is a Spring Bean?

A **Bean** is an object that is created and managed by the Spring IoC container.

For example:

```java
@Service
public class PaymentService {
}
```

Spring creates a `PaymentService` object and manages it.

```text
Spring IoC Container
        |
        ├── PaymentService bean
        ├── OrderService bean
        └── UserService bean
```

The container is commonly called **ApplicationContext**.

---

# 4. How does Spring know what to create?

Spring Boot scans your packages for annotations such as:

```java
@Component
@Service
@Repository
@Controller
@RestController
```

These classes become Spring Beans.

For example:

```java
@Service
public class PaymentService {

    public void pay() {
        System.out.println("Payment completed");
    }
}
```

Then:

```java
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void createOrder() {
        System.out.println("Order created");
        paymentService.pay();
    }
}
```

Spring automatically connects them.

# 5. Spring App – Full Working Example

Create a Spring Boot project with **Spring Web** dependency.

### Project structure

```text
spring-ioc-demo
└── src/main/java/com/example/demo
    ├── DemoApplication.java
    ├── PaymentService.java
    └── OrderService.java
```

### `DemoApplication.java`

```java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

### `PaymentService.java`

```java
package com.example.demo;

import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    public void pay() {
        System.out.println("Payment completed");
    }
}
```

### `OrderService.java`

```java
package com.example.demo;

import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void createOrder() {
        System.out.println("Order created");
        paymentService.pay();
    }
}
```

### Run and test

To execute `OrderService`, we can get it from Spring's container:

```java
package com.example.demo;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication implements CommandLineRunner {

    private final OrderService orderService;

    public DemoApplication(OrderService orderService) {
        this.orderService = orderService;
    }

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    @Override
    public void run(String... args) {
        orderService.createOrder();
    }
}
```

Output:

```text
Order created
Payment completed
```

### What happened internally?

```text
SpringApplication.run()
        ↓
Spring starts ApplicationContext
        ↓
Scans @Service classes
        ↓
Creates PaymentService bean
        ↓
Creates OrderService bean
        ↓
Sees OrderService needs PaymentService
        ↓
Injects PaymentService
        ↓
Application starts
```

# 6. Why is this useful?

Without Spring:

```java
class OrderService {

    private PaymentService paymentService =
            new PaymentService();
}
```

If later you want:

```text
PaymentService
       ↓
StripePaymentService
```

you have to modify the class.

With DI + interfaces:

```java
public interface PaymentService {
    void pay();
}
```

```java
@Service
public class UpiPaymentService implements PaymentService {

    @Override
    public void pay() {
        System.out.println("Paid using UPI");
    }
}
```

```java
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Now `OrderService` depends on the **abstraction**, not a concrete implementation.

This is one of the most important ideas you'll use throughout Spring Boot.

## 7. IoC vs DI — Important Interview Question

| Concept                   | Meaning                                           |
| ------------------------- | ------------------------------------------------- |
| **IoC**                   | Spring takes control of object creation/lifecycle |
| **DI**                    | Spring supplies required dependencies to objects  |
| **Bean**                  | Object managed by Spring                          |
| **ApplicationContext**    | Spring IoC container                              |
| **Constructor Injection** | Dependency supplied through constructor           |

Think:

```text
IoC = Who controls object creation?
      → Spring

DI = How does Spring give dependencies?
     → Injection
```

### React comparison

You can loosely think of it like:

```text
React
Component
   ↓
receives props
```

while Spring does:

```text
Spring
OrderService
   ↓
receives PaymentService
```

But Spring DI is much more powerful because Spring also manages the **lifecycle, configuration, scopes, proxies, and wiring** of those objects.

---

### Key points to remember

1. **IoC** → control of object creation moves from your code to Spring.
2. **DI** → Spring injects required objects.
3. Prefer **constructor injection**.
4. `@Service`, `@Repository`, `@Component`, etc. create Spring-managed beans through component scanning.
5. **ApplicationContext** is the main IoC container in Spring Boot.
6. Avoid manually doing `new PaymentService()` for Spring-managed dependencies.
7. Interfaces + DI give you **loose coupling** and easier testing.
8. This concept is the foundation for **Spring MVC, Spring Data JPA, Security, configuration, and almost everything else in Spring Boot**.
