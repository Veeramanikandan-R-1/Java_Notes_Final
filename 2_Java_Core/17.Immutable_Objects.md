## Immutable Objects — Mutable vs Immutable

The easiest way to understand this:

> **Mutable object = its state can be changed after creation.**
> **Immutable object = its state cannot be changed after creation.**

### 1. Mutable Object

A mutable object's fields can be modified after the object is created.

```java
class User {
    String name;

    User(String name) {
        this.name = name;
    }
}

public class Main {
    public static void main(String[] args) {
        User user = new User("John");

        user.name = "David";  // State changed

        System.out.println(user.name); // David
    }
}
```

Here, the **same `User` object** was modified.

```text
Before: User { name = "John" }
                 ↓
            name changed
                 ↓
After:  User { name = "David" }
```

So `User` is **mutable**.

---

### 2. Immutable Object

Once an immutable object is created, its state **cannot be changed**.

A classic Java example is `String`.

```java
String name = "John";

name = "David";
```

It looks like `name` changed, but actually **the original String object was not changed**.

Conceptually:

```text
"John"  ← original String object
   ↓
"David" ← new String object
```

```java
String name = "John";

name.concat(" Smith");

System.out.println(name); // John
```

`concat()` doesn't modify `"John"`. It returns a **new String**.

```java
String name = "John";

name = name.concat(" Smith");

System.out.println(name); // John Smith
```

---

## 3. Mutable vs Immutable

|                                 | Mutable                      | Immutable                        |
| ------------------------------- | ---------------------------- | -------------------------------- |
| State can change?               | ✅ Yes                        | ❌ No                             |
| Same object modified?           | ✅ Yes                        | ❌ No                             |
| New object required for change? | Usually ❌                    | ✅ Yes                            |
| Example                         | `StringBuilder`, `ArrayList` | `String`, `Integer`, `LocalDate` |
| Thread-safety                   | Can require synchronization  | Easier to use safely             |

### Important distinction

```java
StringBuilder sb = new StringBuilder("Hello");

sb.append(" World");

System.out.println(sb); // Hello World
```

`StringBuilder` is **mutable** because `append()` changes the same object.

Whereas:

```java
String s = "Hello";

s.concat(" World");

System.out.println(s); // Hello
```

`String` is **immutable**.

## 4. Why do we need Immutable Objects?

Main advantages:

### 🔹 1. Thread-safe by design

Multiple threads can safely read an immutable object because nobody can modify its state.

### 🔹 2. Predictable

Once created:

```java
String name = "John";
```

You know `"John"` will always represent `"John"`.

### 🔹 3. Good for HashMap keys

Immutable objects are safer as keys:

```java
Map<String, Integer> map = new HashMap<>();

map.put("John", 100);
```

If the key's state could unexpectedly change, lookup/hash-based collections could behave incorrectly.

### 🔹 4. Useful in Spring Boot

Immutable objects are commonly used for:

* DTOs
* Configuration objects
* Value objects
* Records
* Domain models where state shouldn't change

## DTO in Java

**DTO = Data Transfer Object**

A DTO is a simple Java object used to **transfer data between different layers or systems**, especially between a **Spring Boot backend and frontend**.

Since you know React, think of a DTO as the **shape of data you send/receive through an API**.

### Example

Suppose React sends:

```json
{
  "name": "John",
  "email": "john@gmail.com",
  "age": 25
}
```

In Spring Boot, you can represent this using a DTO:

```java
public class UserDTO {

    private String name;
    private String email;
    private int age;

    // constructor, getters, setters
}
```

Then your controller can receive it:

```java
@PostMapping("/users")
public UserDTO createUser(@RequestBody UserDTO user) {
    System.out.println(user.getName());
    return user;
}
```

### Why not directly use Entity?

Suppose your database entity is:

```java
@Entity
public class User {

    private Long id;
    private String name;
    private String email;
    private String password;
}
```

You **shouldn't normally send this entity directly to React**, because it contains sensitive/internal fields like `password`.

Instead:

```text
Database
   ↓
User Entity
   ↓
Service
   ↓
UserDTO
   ↓
Controller
   ↓
JSON
   ↓
React
```

For example:

```java
public class UserDTO {
    private String name;
    private String email;
}
```

Now the API returns:

```json
{
  "name": "John",
  "email": "john@gmail.com"
}
```

The password never leaves the backend.

### DTO vs Entity

| DTO                       | Entity                     |
| ------------------------- | -------------------------- |
| Used for data transfer    | Represents database table  |
| API request/response      | Database persistence       |
| Can hide sensitive fields | Usually contains DB fields |
| Doesn't need `@Entity`    | Uses `@Entity`             |
| Defines API contract      | Defines DB model           |

### In Spring Boot

You'll commonly see:

```text
Controller
    ↓
DTO
    ↓
Service
    ↓
Entity
    ↓
Repository
    ↓
Database
```

**Interview definition:**

> A DTO is an object used to transfer data between application layers or systems without exposing the underlying domain/entity structure.

**For your React → Spring Boot learning:** DTOs are especially important when learning **REST APIs, Entity, Service, Controller, and JPA**.

## 5. How to Create an Immutable Class

Typical rules:

1. Make class `final`
2. Make fields `private final`
3. Initialize fields through constructor
4. Don't provide setters
5. For mutable fields, make **defensive copies**

Simple example:

```java
final class User {

    private final String name;
    private final int age;

    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String getName() {
        return name;
    }

    public int getAge() {
        return age;
    }
}
```

Usage:

```java
User user = new User("John", 25);

// user.name = "David";  // ❌ Cannot access
// user.setName("David"); // ❌ No setter
```

Once created:

```text
User
 ├── name = "John"   ← cannot change
 └── age  = 25       ← cannot change
```

### Interview point ⭐

**`final` reference ≠ immutable object.**

```java
final User user = new User("John", 25);
```

`final` means you cannot make `user` refer to another object:

```java
user = new User("David", 30); // ❌
```

But if `User` itself is mutable:

```java
user.setName("David"); // ✅
```

So **immutability is a property of the object's design, not simply the `final` keyword.**

### Remember this

> **Mutable → change the existing object.**
> **Immutable → create/use a new object when a different state is needed.**

Next important concept after this is **how to make an immutable class when it contains mutable objects like `List`, `Date`, or `ArrayList`**—this is where **defensive copying** becomes important.
