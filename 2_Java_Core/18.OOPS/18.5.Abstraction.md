## Java OOP — Abstraction

**Abstraction = hiding implementation details and exposing only what is necessary.**

Think about your React experience:

```text
You call an API:
fetch("/users")
```

You don't care internally how HTTP connection, headers, parsing, etc. are implemented. You just use the exposed functionality.

Java abstraction follows the same idea.

---

# 1. How Java achieves Abstraction

Java mainly provides **two ways**:

```text
Abstraction
├── Abstract class
└── Interface ⭐
```

---

# 2. Abstract Class

Use the `abstract` keyword.

```java id="x9p2kd"
abstract class Animal {

    // Abstract method - no implementation
    abstract void sound();

    // Concrete method - has implementation
    void eat() {
        System.out.println("Eating...");
    }
}
```

A child class must implement the abstract method:

```java id="h7q3lm"
class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Bark");
    }
}
```

Usage:

```java id="a4k8zn"
Dog dog = new Dog();

dog.sound();  // Bark
dog.eat();    // Eating...
```

### Important

You **cannot create an object of an abstract class**:

```java id="p2x7qw"
Animal animal = new Animal(); // ❌
```

But you **can have a reference**:

```java id="v5n3rt"
Animal animal = new Dog(); // ✅
animal.sound();            // Bark
```

This combines **abstraction + polymorphism**.

---

# 3. Abstract Class Can Have

An abstract class can contain:

* Abstract methods
* Concrete methods
* Fields
* Constructors
* Static methods
* Final methods

Example:

```java id="k6m1pq"
abstract class Vehicle {

    String brand;

    Vehicle(String brand) {
        this.brand = brand;
    }

    abstract void start();

    void stop() {
        System.out.println("Vehicle stopped");
    }
}
```

---

# 4. Interface ⭐⭐⭐

An interface is commonly used to define a **contract**.

```java id="r8c4vx"
interface PaymentService {

    void pay();
}
```

Implementation:

```java id="n3d7ks"
class UpiPayment implements PaymentService {

    @Override
    public void pay() {
        System.out.println("Payment using UPI");
    }
}
```

Usage:

```java id="b6f2mw"
PaymentService payment = new UpiPayment();

payment.pay();
```

Output:

```text
Payment using UPI
```

The interface says:

> "Any payment service must provide `pay()`."

It doesn't care **how** payment happens.

---

# 5. Interface vs Abstract Class

| Abstract Class                      | Interface                                   |
| ----------------------------------- | ------------------------------------------- |
| `abstract class`                    | `interface`                                 |
| `extends`                           | `implements`                                |
| Can have state/fields               | Mainly contract                             |
| Can have constructor                | No constructor                              |
| Abstract + concrete methods         | Abstract + default/static methods           |
| Class can extend only **one** class | Class can implement **multiple** interfaces |

Example:

```java
class UpiPayment implements PaymentService, RefundService {
}
```

This is allowed.

---

# 6. Why Abstraction is Useful in Spring Boot ⭐⭐⭐

You'll see this pattern constantly:

```java
public interface UserService {
    User getUserById(Long id);
}
```

Implementation:

```java
@Service
public class UserServiceImpl implements UserService {

    @Override
    public User getUserById(Long id) {
        // actual business logic
        return ...;
    }
}
```

Controller depends on the **abstraction**:

```java
private final UserService userService;
```

The controller doesn't need to know the internal implementation.

This gives:

* Loose coupling
* Easier testing
* Easier replacement of implementations
* Cleaner architecture
* Dependency Injection

# 7. Abstraction vs Encapsulation ⭐

These are often confused.

### Encapsulation

**Hide/protect data and control access.**

```java
private String password;

public String getPassword() {
    return password;
}
```

### Abstraction

**Hide implementation complexity and expose essential behavior.**

```java
interface PaymentService {
    void pay();
}
```

Think:

```text
Encapsulation → HOW data is accessed/protected
Abstraction   → WHAT functionality is exposed
```

## 🔑 Interview Cheat Sheet

```text
Abstraction
│
├── Hides implementation details
├── Shows only essential functionality
│
├── Abstract class
│    ├── Can have abstract + concrete methods
│    ├── Can have constructor
│    └── Cannot instantiate directly
│
└── Interface
     ├── Defines a contract
     ├── implements keyword
     └── Multiple interfaces supported
```

### Most important for Spring Boot

Remember this pattern:

```java
interface Service {
    void doSomething();
}

class ServiceImpl implements Service {
    @Override
    public void doSomething() {
        // implementation
    }
}
```

**Interface = what to do**
**Implementation = how to do it**

That's the abstraction pattern you'll encounter repeatedly in Spring Boot.

---

Q. when we have abstract class what is the need for interface?

Yes, this is a **very important question**. If abstract classes already provide abstraction, why did Java need interfaces?

The key reason is:

> **Java allows a class to extend only ONE class, but it can implement MULTIPLE interfaces.**

### 1. Abstract class gives abstraction + shared implementation

Suppose:

```java
abstract class Animal {
    void eat() {
        System.out.println("Eating");
    }

    abstract void sound();
}
```

```java
class Dog extends Animal {
    @Override
    void sound() {
        System.out.println("Bark");
    }
}
```

Here `Dog` gets **common functionality** (`eat()`) from `Animal`.

So abstract class is useful when classes have a strong **IS-A relationship + shared code/state**.

---

### 2. Interface is useful for defining capabilities/contracts

Imagine:

```java
interface Flyable {
    void fly();
}

interface Swimmable {
    void swim();
}
```

Now:

```java
class Duck implements Flyable, Swimmable {

    @Override
    public void fly() {
        System.out.println("Flying");
    }

    @Override
    public void swim() {
        System.out.println("Swimming");
    }
}
```

A Duck can have **multiple capabilities**:

```text
Duck
 ├── Flyable
 └── Swimmable
```

You cannot achieve this with abstract classes:

```java
class Duck extends Flyable, Swimmable { } // ❌
```

---

# 3. The biggest practical difference

Imagine:

```java
abstract class Animal {
    abstract void eat();
}

interface Flyable {
    void fly();
}

class Bird extends Animal implements Flyable {

    @Override
    void eat() {
        System.out.println("Eating");
    }

    @Override
    public void fly() {
        System.out.println("Flying");
    }
}
```

Here:

* `Animal` → **what Bird fundamentally is**
* `Flyable` → **what Bird can do**

That's a very useful mental model:

> **Abstract class = "IS-A" + shared implementation**
> **Interface = "CAN-DO" / contract**

---

# 4. Why interfaces are extremely important in Spring Boot ⭐⭐⭐

Suppose you have:

```java
interface PaymentService {
    void pay();
}
```

You can have multiple implementations:

```java
class UpiPayment implements PaymentService {
    public void pay() {
        System.out.println("UPI");
    }
}

class CardPayment implements PaymentService {
    public void pay() {
        System.out.println("Card");
    }
}
```

Your controller/service can depend on:

```java
PaymentService paymentService;
```

It doesn't care whether the implementation is UPI, Card, etc.

This is one of the foundations of **loose coupling + dependency injection** in Spring.

---

## 🧠 Simple comparison

|                          | Abstract Class            | Interface                     |
| ------------------------ | ------------------------- | ----------------------------- |
| Main purpose             | Shared base + abstraction | Contract/capability           |
| Multiple inheritance     | ❌                         | ✅ Multiple interfaces         |
| Can have instance fields | ✅                         | ❌*                            |
| Constructor              | ✅                         | ❌                             |
| Concrete methods         | ✅                         | ✅ (`default`, `static`, etc.) |
| Keyword                  | `extends`                 | `implements`                  |
| Spring usage             | Sometimes                 | **Very common**               |

* Interfaces can have constants (`public static final`), but not normal per-object instance state.

### ⭐ What to remember for interviews

Don't think:

> "Interface is another way of making an abstract class."

Instead think:

```text
Abstract class → shared foundation
Interface     → contract/capability
```

And in real Spring Boot applications, **interfaces are heavily used because they help create loosely coupled, replaceable implementations.**
