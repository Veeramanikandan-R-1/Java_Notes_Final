## Java OOP — Polymorphism

**Polymorphism = "one thing, many forms."**

In Java, the same method/interface/reference can behave differently depending on the actual object.

For your Spring Boot goal, **runtime polymorphism is especially important**.

---

## 1. Two Types of Polymorphism

```text
Polymorphism
├── Compile-time → Method Overloading
└── Runtime      → Method Overriding
```

---

# 2. Compile-Time Polymorphism — Method Overloading

Same method name, but **different parameters**.

```java
class Calculator {

    int add(int a, int b) {
        return a + b;
    }

    int add(int a, int b, int c) {
        return a + b + c;
    }

    double add(double a, double b) {
        return a + b;
    }
}
```

Usage:

```java
Calculator calc = new Calculator();

System.out.println(calc.add(10, 20));       // 30
System.out.println(calc.add(10, 20, 30));   // 60
System.out.println(calc.add(10.5, 20.5));   // 31.0
```

Java decides **which method to call at compile time** based on the arguments.

### Important

Overloading can differ by:

* Number of parameters
* Parameter types
* Parameter order

Return type **alone cannot create overloading**.

```java
int add(int a, int b) { }
double add(int a, int b) { } // ❌
```

# 3. Runtime Polymorphism — Method Overriding ⭐

A child class provides its own implementation of a parent method.

```java
class Animal {

    void sound() {
        System.out.println("Animal sound");
    }
}

class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Bark");
    }
}

class Cat extends Animal {

    @Override
    void sound() {
        System.out.println("Meow");
    }
}
```

Now:

```java
Animal a1 = new Dog();
Animal a2 = new Cat();

a1.sound(); // Bark
a2.sound(); // Meow
```

Although both references are `Animal`, Java looks at the **actual object** at runtime.

```text
Animal a1 = new Dog();
             ↑
       actual object

a1.sound()
   ↓
Dog.sound()
```

This is called:

> **Runtime polymorphism / Dynamic Method Dispatch**

---

# 4. Why is this Important in Spring Boot? ⭐⭐⭐

You'll frequently see:

```java
PaymentService service = new CreditCardPayment();
```

Suppose:

```java
interface PaymentService {
    void pay();
}

class CreditCardPayment implements PaymentService {

    @Override
    public void pay() {
        System.out.println("Paid using Credit Card");
    }
}

class UpiPayment implements PaymentService {

    @Override
    public void pay() {
        System.out.println("Paid using UPI");
    }
}
```

Then:

```java
PaymentService service = new UpiPayment();

service.pay();
```

Output:

```text
Paid using UPI
```

You program against the **interface**, while the actual implementation can change.

This design is heavily used with **Spring dependency injection**.

---

# 5. Overloading vs Overriding

|                      | Overloading                     | Overriding     |
| -------------------- | ------------------------------- | -------------- |
| Polymorphism         | Compile-time                    | Runtime        |
| Where                | Same class usually              | Parent → Child |
| Method name          | Same                            | Same           |
| Parameters           | Must differ                     | Must be same   |
| Return type          | Can differ if parameters differ | Same/covariant |
| Inheritance required | ❌                               | ✅              |
| `@Override`          | ❌                               | ✅ recommended  |

---

## 6. Important Rules for Overriding

### `private` methods cannot be overridden

```java
class Parent {
    private void test() {}
}

class Child extends Parent {
    // Not overriding test()
    private void test() {}
}
```

They are separate methods.

### `final` methods cannot be overridden

```java
class Parent {
    final void test() {}
}

class Child extends Parent {
    // void test() {} // ❌
}
```

### `static` methods are not overridden

Static methods are **hidden**, not overridden.

## 🔑 Remember This

```text
Polymorphism
│
├── Compile-time
│     └── Overloading
│
└── Runtime
      └── Overriding
            ├── Parent reference
            ├── Child object
            └── Child method executes
```

The most important pattern to remember:

```java
Parent ref = new Child();
ref.method();
```

If `Child` **overrides** `method()`, the **Child implementation executes**.

👉 For Spring Boot, this concept connects directly to **interfaces + implementations + dependency injection**, so make sure runtime polymorphism is very clear before moving on.

---

Exactly! **`@Override` is not what makes overriding happen.** The overriding happens because of the **method signature + inheritance**.

### Without `@Override`

```java
class Animal {
    void sound() {
        System.out.println("Animal sound");
    }
}

class Dog extends Animal {

    void sound() {  // No @Override
        System.out.println("Bark");
    }
}

Animal animal = new Dog();

animal.sound();
```

Output:

```text
Bark
```

Why?

Because Java sees:

```text
Animal
  ↑
 Dog
```

`Dog` has a method with the **same signature** as `Animal.sound()`.

So Java treats it as an override automatically.

---

### Then why do we use `@Override`? ⭐

`@Override` is basically a **compiler check + documentation**.

```java
class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Bark");
    }
}
```

It tells the compiler:

> "I intend to override a parent method. Please verify it."

For example, suppose you accidentally write:

```java
class Dog extends Animal {

    @Override
    void sounds() {   // ❌ typo
        System.out.println("Bark");
    }
}
```

Compiler will catch it:

```text
method does not override or implement a method from a supertype
```

Without `@Override`:

```java
class Dog extends Animal {

    void sounds() {   // Different method
        System.out.println("Bark");
    }
}
```

This compiles, but **you didn't actually override `sound()`**.

### 🧠 Simple rule

> **`@Override` doesn't perform overriding. It verifies that you are actually overriding.**

Think of it like TypeScript's type checking: it doesn't create the behavior; it helps catch mistakes.
