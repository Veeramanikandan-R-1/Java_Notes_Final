## LVTI (Local Variable Type Inference) in Java

LVTI was introduced in Java 10. It allows you to use the `var` keyword so the compiler infers a local variable's type from its initializer.

### 1. Basic example

```
public class Main {
    public static void main(String[] args) {
        var name = "Java";       // String
        var age = 25;            // int
        var price = 99.5;        // double

        System.out.println(name);
        System.out.println(age);
        System.out.println(price);
    }
}
```

The compiler determines each variable's type at compile time. `var` does not make Java dynamically typed.

### 2. With collections

```
import java.util.*;

public class Main {
    public static void main(String[] args) {
        var names = new ArrayList<String>();
        names.add("Arun");
        names.add("Kumar");

        for (var name : names) {
            System.out.println(name);
        }
    }
}
```

Here, `names` is inferred as `ArrayList<String>`, and `name` is inferred as `String`.

### 3. Rules of `var`

| Valid                           | Invalid                                          |
| ------------------------------- | ------------------------------------------------ |
| `var age = 25;`                 | `var age;` — no initializer                      |
| `var name = "Java";`            | `var value = null;` — type cannot be inferred    |
| `var list = new ArrayList<>();` | `class Test { var x = 10; }` — field declaration |
| `for (var item : list)`         | `var a = 10, b = 20;` — multiple declarators     |

Important: `var` is allowed only for local variables (including loop variables and try-with-resources variables), not method parameters, return types, or instance/static fields.

### 4. `var` vs dynamic typing

```
var value = 10;    // Inferred as int
// value = "Java"; // Compilation error
```

Once inferred, the variable's type cannot change.

### Interview points

- Introduced in Java 10.
- Uses compile-time type inference.
- `var` is a reserved type name, not a new data type.
- Improves readability when the type is obvious.
- Cannot be used without an initializer, with only `null`, or for fields and method parameters.

## Why is LVTI (`var`) allowed only for local variables in Java?

Main reason: Local variables have an initializer that the compiler can use to infer the type easily, while allowing inference for fields and method parameters could make declarations less clear and more complicated.

### 1. Local variable — allowed

```
public void display() {
    var name = "Java";  // Compiler infers String
    var age = 25;       // Compiler infers int
}
```

The compiler can infer the type directly from the initializer.

### 2. Instance variable — not allowed

```
class Employee {
    // var name = "Arun"; // Compilation error
    String name = "Arun"; // Valid
}
```

Fields are part of a class's structure. Their types should be explicit in the class declaration for clarity and reliable type checking.

### 3. Method parameter — not allowed

```
// Invalid
// void display(var name) { }

void display(String name) { } // Valid
```

A method's parameter types define its signature, which the compiler needs to determine method calls and overload resolution.

### 4. Return type — not allowed

```
// Invalid
// var getName() { return "Java"; }

String getName() {
    return "Java";
}
```

The return type is part of the method contract, so Java requires it to be explicitly declared.

### Interview answer

LVTI is restricted to local variables because their types can be inferred from initializers without changing Java's static type system. Fields, parameters, and return types remain explicitly typed to preserve clear class structures and method contracts.

Good question. Actually, Java's compiler can infer types in other places too. The restriction on `var` is a Java language design decision, not a limitation of the compiler.

Let's understand with examples.

### 1. Java already supports type inference elsewhere

A. Generic type inference

```
List<String> names = new ArrayList<>();
```

The compiler infers that `ArrayList<>` should use `String` from the left-hand side.

B. Lambda expressions

```
Function<String, Integer> length = s -> s.length();
```

The compiler infers that `s` is a `String` from the functional interface.

C. Method return type inference

```
var result = getName();

static String getName() {
    return "Java";
}
```

The compiler infers `result` as `String` from the method's declared return type.

### 2. Then why restrict `var` to local variables?

Consider a class field:

```
class Employee {
    var name = "Arun"; // Not allowed
}
```

The compiler could infer `String` here. Java simply does not permit this syntax.

Reasons include:

- Readability: Class fields and method signatures define a class's public structure. Explicit types make that structure easier to understand.
- API clarity: Parameter and return types are important parts of method contracts.
- Language simplicity: Restricting `var` to local variables keeps its rules predictable and avoids introducing broader inference rules for class members.

One important distinction: Java does not require every type to be written explicitly. It already infers types in generics, lambdas, and local variables. `var` just extends that convenience to local variable declarations.

### Interview answer

Java restricts LVTI (`var`) to local variables by design, not because the compiler cannot infer field or parameter types. Java already supports type inference in several contexts, but keeps class fields, method parameters, and return types explicit for clear declarations and method contracts.
