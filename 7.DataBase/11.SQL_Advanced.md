# Database — SQL Advanced

For your **Java + Spring Boot** goal, these features are important to understand conceptually. In modern Spring Boot applications, business logic is usually kept in Java rather than heavily inside stored procedures/triggers, but you will encounter these in existing enterprise systems.

I'll use **MySQL syntax** because you've been practicing MySQL. PostgreSQL has similar concepts but some syntax differs.

---

# 1. Views

A **View** is a saved SQL query that behaves like a virtual table.

### Tables

```sql
employees
+----+-------+--------+---------------+
| id | name  | salary | department_id |
+----+-------+--------+---------------+

departments
+----+-------------+
| id | name        |
+----+-------------+
```

Create a view:

```sql
CREATE VIEW employee_details AS
SELECT
    e.id,
    e.name,
    e.salary,
    d.name AS department
FROM employees e
JOIN departments d
    ON e.department_id = d.id;
```

Now use it like a table:

```sql
SELECT *
FROM employee_details;
```

### Why use Views?

Instead of repeatedly writing:

```sql
SELECT ...
FROM employees
JOIN departments ...
```

you can simply:

```sql
SELECT *
FROM employee_details;
```

### Important

A normal view **doesn't usually store a separate copy of the data**.

```text
View
 ↓
Saved SQL query
 ↓
Underlying tables
```

If underlying data changes, the view normally reflects it.

### When useful

* Simplifying complex queries
* Hiding unnecessary columns
* Providing controlled access to data
* Reusing complex queries

# 2. Stored Procedures

A **Stored Procedure** is a group of SQL statements stored inside the database and executed by calling it.

Example:

```sql
DELIMITER //

CREATE PROCEDURE get_employees_by_department(
    IN dept_id INT
)
BEGIN
    SELECT *
    FROM employees
    WHERE department_id = dept_id;
END //

DELIMITER ;
```

Call it:

```sql
CALL get_employees_by_department(1);
```

### Parameters

```text
IN      → input
OUT     → output
INOUT   → input + output
```

Example:

```sql
CREATE PROCEDURE get_employee_count(
    IN dept_id INT,
    OUT total INT
)
BEGIN
    SELECT COUNT(*)
    INTO total
    FROM employees
    WHERE department_id = dept_id;
END;
```

Call:

```sql
CALL get_employee_count(1, @total);

SELECT @total;
```

### Why procedures?

Useful for:

* Complex database operations
* Batch operations
* Legacy enterprise systems
* Operations that need to execute close to the data

But in Spring Boot, don't automatically put business logic into procedures.

Often:

```text
Spring Boot Service
       ↓
Repository
       ↓
Database
```

is preferred for application business logic.

# 3. Functions

A **Function** accepts input and **returns a value**.

Example:

```sql
DELIMITER //

CREATE FUNCTION calculate_bonus(
    salary DECIMAL(10,2)
)
RETURNS DECIMAL(10,2)
DETERMINISTIC
BEGIN
    RETURN salary * 0.10;
END //

DELIMITER ;
```

Use it:

```sql
SELECT
    name,
    salary,
    calculate_bonus(salary) AS bonus
FROM employees;
```

Result conceptually:

```text
John    70000    7000
David   60000    6000
```

### Procedure vs Function

|                          | Procedure         | Function               |
| ------------------------ | ----------------- | ---------------------- |
| Called with              | `CALL`            | Used in SQL expression |
| Must return value?       | No                | Yes                    |
| Can be used in `SELECT`? | No                | Yes                    |
| Typical use              | Perform operation | Calculate/return value |

Think:

```text
Procedure → "Do something"

Function  → "Give me a value"
```

# 4. Triggers

A **Trigger automatically executes when a database event occurs.**

For example:

```text
INSERT
UPDATE
DELETE
```

Suppose you want to maintain an employee audit table.

### Audit table

```sql
CREATE TABLE employee_audit (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    employee_id BIGINT,
    action VARCHAR(20),
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Create trigger:

```sql
DELIMITER //

CREATE TRIGGER employee_after_insert
AFTER INSERT ON employees
FOR EACH ROW
BEGIN
    INSERT INTO employee_audit(employee_id, action)
    VALUES (NEW.id, 'INSERT');
END //

DELIMITER ;
```

Now:

```sql
INSERT INTO employees
(name, email, salary, department_id)
VALUES
('John', 'john@gmail.com', 70000, 1);
```

The trigger automatically executes.

Check:

```sql
SELECT *
FROM employee_audit;
```

You'll see something like:

```text
employee_id | action | changed_at
------------+--------+-------------------
5           | INSERT | 2026-09-24 22:00:00
```

### `NEW` and `OLD`

For triggers:

```text
NEW → new row
OLD → previous row
```

For example, during an UPDATE:

```sql
OLD.salary
NEW.salary
```

can be used to compare the old and new values.

### Important warning

Triggers can make systems difficult to understand because something happens **automatically behind the application's back**.

For example:

```text
Java code
   ↓
UPDATE employee
   ↓
Trigger automatically executes
   ↓
Audit table changes
```

Therefore, use them carefully.

# 5. Sequences

A **Sequence generates a series of unique numbers**.

This concept is especially important in **PostgreSQL**.

Example PostgreSQL:

```sql
CREATE SEQUENCE employee_id_seq
START 1
INCREMENT 1;
```

Get next value:

```sql
SELECT nextval('employee_id_seq');
```

Result:

```text
1
```

Next:

```sql
SELECT nextval('employee_id_seq');
```

Result:

```text
2
```

### Why?

Useful for generating identifiers:

```text
1
2
3
4
5
...
```

### PostgreSQL

You will commonly see:

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY
```

instead of manually managing sequences.

Older PostgreSQL code may also use:

```sql
SERIAL
BIGSERIAL
```

which are backed by sequences.

### MySQL difference

MySQL typically uses:

```sql
id BIGINT AUTO_INCREMENT PRIMARY KEY
```

rather than PostgreSQL's traditional sequence-based approach.

# 7. Advanced SQL Exercise 1 — Second Highest Salary

```sql
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (
    SELECT MAX(salary)
    FROM employees
);
```

If salaries are:

```text
90000
80000
70000
60000
```

result:

```text
80000
```

---

# 8. Exercise 2 — Employees Earning Above Department Average

```sql
SELECT e.name, e.salary, e.department_id
FROM employees e
WHERE e.salary > (
    SELECT AVG(e2.salary)
    FROM employees e2
    WHERE e2.department_id = e.department_id
);
```

This is a **correlated subquery**.

Conceptually:

```text
For each employee
      ↓
Calculate that employee's department average
      ↓
Compare employee salary
```

---

# 9. Exercise 3 — Department With Highest Average Salary

```sql
SELECT
    department_id,
    AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id
ORDER BY avg_salary DESC
LIMIT 1;
```

# 10. Exercise 4 — Employees With No Department

Using `LEFT JOIN`:

```sql
SELECT e.*
FROM employees e
LEFT JOIN departments d
    ON e.department_id = d.id
WHERE d.id IS NULL;
```

This is a very common interview question.

---

# 11. Exercise 5 — Rank Employees by Salary

Use a **window function**:

```sql
SELECT
    name,
    salary,
    RANK() OVER (ORDER BY salary DESC) AS salary_rank
FROM employees;
```

Example:

```text
name    salary   salary_rank
------  -------  -----------
John    90000    1
David   80000    2
Mary    80000    2
Peter   70000    4
```

Notice that `RANK()` gives the same rank to equal salaries and leaves a gap afterward.

---

# 12. Exercise 6 — Highest Paid Employee in Each Department

```sql
SELECT *
FROM (
    SELECT
        e.*,
        RANK() OVER (
            PARTITION BY department_id
            ORDER BY salary DESC
        ) AS salary_rank
    FROM employees e
) x
WHERE salary_rank = 1;
```

This is an **important advanced SQL pattern**.

```text
PARTITION BY department_id
        ↓
Separate employees by department

ORDER BY salary DESC
        ↓
Highest salary first

RANK()
        ↓
Assign ranking
```

# What you should remember for interviews

### Views

> A view is a virtual table based on a stored SQL query.

### Stored Procedure

> A stored procedure is a stored set of SQL statements that can perform database operations and accept parameters.

### Function

> A database function accepts parameters and returns a value.

### Trigger

> A trigger automatically executes in response to database events such as INSERT, UPDATE, or DELETE.

### Sequence

> A sequence generates sequential numeric values, commonly used for identifiers in PostgreSQL.

### Advanced SQL

Focus heavily on:

```text
JOINs
Subqueries
Correlated subqueries
CTEs
Window functions
GROUP BY / HAVING
CASE
EXISTS
UNION / UNION ALL
Indexes
Transactions
Execution plans
```

For your **Spring Boot** path, the next important connection is:

```text
Advanced SQL
     ↓
JDBC
     ↓
JPA / Hibernate
     ↓
Spring Data JPA
     ↓
Custom Queries (@Query)
     ↓
Native SQL
     ↓
Spring Boot REST API
```

That is where these database concepts become directly useful in your Java backend work.
