## Database Indexes — Query Optimization

Since you're moving from **React → Java/Spring Boot**, think of a database index like a **Java `HashMap` lookup structure**: instead of scanning everything, the DB can quickly locate the required rows.

---

Exactly. The important thing is to understand **what gets created when you run `CREATE INDEX`**.

Suppose you have:

```sql
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    email VARCHAR(100)
);
```

And 1 million rows.

You run:

```sql
CREATE INDEX idx_email ON employees(email);
```

## 1. What actually happens?

The database creates a **separate data structure** for `email`.

For a typical MySQL B-tree index, conceptually it looks something like:

```text
                 [M]
                /   \
             [D-M]  [N-Z]
              /        \
        [A-C] [D-L]   [N-R] [S-Z]
```

The actual structure is more complex, but this is the basic idea.

The index contains values from your column in an **organized/searchable structure**, along with references to the corresponding table rows.

For example:

```text
Index on email

aaron@gmail.com   → row location
bob@gmail.com     → row location
john@gmail.com    → row location
ravi@gmail.com    → row location
...
```

The important part is:

> The database doesn't have to scan the entire table to find `john@gmail.com`.

---

# 2. Without index

Suppose the table contains:

```text
Row 1  → aaron@gmail.com
Row 2  → ravi@gmail.com
Row 3  → kumar@gmail.com
Row 4  → john@gmail.com
...
Row 1,000,000
```

Query:

```sql
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

Without an index, the database may do:

```text
Check row 1
    ↓
Check row 2
    ↓
Check row 3
    ↓
Check row 4 → FOUND!
```

For a value near the end:

```text
Check row 1
Check row 2
Check row 3
...
Check row 1,000,000
```

That's a **table scan**.

---

# 3. With index

Now imagine the index is organized like a tree:

```text
                    M
                  /   \
                D       R
              /  \     / \
             B    H   P   W
```

Looking for:

```text
john@gmail.com
```

The database doesn't randomly search everything.

It navigates through the tree:

```text
                M
                ↓
         J is before M
                ↓
                D-H area
                ↓
                H → J area
                ↓
           john@gmail.com
                ↓
             row location
                ↓
          Actual table row
```

So instead of checking potentially millions of rows, it follows a relatively small number of index nodes.

---

# 4. Why is this fast?

Because the index has a **tree structure designed for searching**.

For a balanced B-tree, searching is roughly:

```text
O(log N)
```

instead of a full scan:

```text
O(N)
```

For example, very roughly:

```text
1,000,000 rows

Table scan:
potentially ~1,000,000 row checks

Index:
roughly a small number of tree levels
        ↓
find index entry
        ↓
jump to required row
```

The exact number of operations depends on the database, index structure, data distribution, caching, etc., so don't interpret `log N` as literally "only 20 operations" in every case.

---

# 5. The important part: Index doesn't contain the whole row

This is something beginners often misunderstand.

Suppose:

```text
employees
-----------------------------------------
id | name | email | salary | department
```

Index:

```sql
CREATE INDEX idx_email ON employees(email);
```

Conceptually:

```text
INDEX
--------------------------------
email               → row reference

aaron@gmail.com     → row X
john@gmail.com      → row Y
ravi@gmail.com      → row Z
```

Then:

```sql
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

works conceptually like:

```text
Query
 ↓
Search index
 ↓
Find john@gmail.com
 ↓
Get row reference
 ↓
Go to actual table row
 ↓
Return id, name, email, salary, department
```

This is why an index can make searching much faster.

---

# 6. Why does creating the index take time?

When you execute:

```sql
CREATE INDEX idx_email ON employees(email);
```

The database has to:

```text
Read existing email values
        ↓
Organize them into the index structure
        ↓
Store references to table rows
        ↓
Write the index to disk
```

That's why creating an index on a huge table can take significant time.

And when you later insert:

```sql
INSERT INTO employees ...
```

the database has to update the index too.

That's why indexes aren't free.

# 7. Simple real-world analogy

Imagine a **1,000-page book**.

### Without index

Someone asks:

> Find "Java Spring Boot".

You start:

```text
Page 1
Page 2
Page 3
...
Page 800
```

### With an index

The book has an organized index:

```text
Java Spring Boot → Page 742
```

You immediately go:

```text
Index
  ↓
Page 742
```

That's essentially the purpose of a database index.

### One important difference

A database B-tree index isn't simply a book's alphabetical index. It is a **data structure optimized for searching and range operations**, and the database uses it according to the query optimizer's execution plan.

---

## The complete picture

```text
CREATE INDEX
      ↓
Database builds B-tree index
      ↓
Index organizes column values
      ↓
Query comes
      ↓
Optimizer checks whether index is useful
      ↓
Navigate index instead of scanning all rows
      ↓
Find matching index entry
      ↓
Get row location
      ↓
Read actual row
```

So the key concept to remember is:

> **An index doesn't magically make the table smaller. It creates an additional organized lookup structure that allows the database to locate relevant rows without examining every table row.**

---

### 1. What is Query Optimization?

**Query optimization** means making SQL queries execute with **less time, CPU, memory, and disk I/O**.

Example:

```sql
SELECT * FROM employees
WHERE email = 'john@gmail.com';
```

If there are **10 million employees** and `email` has no index, the DB may need to check many/all rows.

With an index:

```sql
CREATE INDEX idx_employee_email
ON employees(email);
```

The database can locate the matching row much faster.

---

# 2. How an Index Helps

Imagine:

```text
employees table
--------------------------------
id    name       email
1     John       john@gmail.com
2     Ravi       ravi@gmail.com
3     Arun       arun@gmail.com
...
10 million rows
```

Without index:

```text
Search row 1
Search row 2
Search row 3
...
Search row 10,000,000
```

This is roughly:

```text
O(N)
```

With an appropriate index, the DB can use an index structure such as a **B-tree**, greatly reducing the amount of data it needs to inspect.

Conceptually:

```text
Index
       john@gmail.com
             ↓
          row → 1
```

---

# 3. Most Important Optimization Rule

### Index columns used frequently in:

* `WHERE`
* `JOIN`
* `ORDER BY`
* `GROUP BY`

Example:

```sql
SELECT *
FROM employees
WHERE department_id = 10;
```

Create:

```sql
CREATE INDEX idx_employee_department
ON employees(department_id);
```

---

# 4. Use `EXPLAIN` — Very Important

Don't blindly create indexes.

Use:

```sql
EXPLAIN
SELECT *
FROM employees
WHERE department_id = 10;
```

Example output may contain:

```text
type: ALL
key: NULL
rows: 1000000
```

`type = ALL` generally indicates a **full table scan**.

After creating an index:

```sql
CREATE INDEX idx_employee_department
ON employees(department_id);
```

Run:

```sql
EXPLAIN
SELECT *
FROM employees
WHERE department_id = 10;
```

You may see something like:

```text
type: ref
key: idx_employee_department
rows: 5000
```

Now the optimizer has chosen the index.

> **Interview point:** `EXPLAIN` is one of the primary tools for understanding how the database plans to execute a query.

---

# 5. Composite Index

Suppose you frequently execute:

```sql
SELECT *
FROM employees
WHERE department_id = 10
AND status = 'ACTIVE';
```

Instead of two separate indexes:

```sql
CREATE INDEX idx_department_status
ON employees(department_id, status);
```

This is a **composite index**.

### Column order matters

```sql
(department_id, status)
```

is generally useful for queries involving:

```sql
department_id
```

and:

```sql
department_id + status
```

But it isn't equivalent to having:

```sql
(status, department_id)
```

The **leftmost-prefix principle** is important.

---

# 6. Index Can Make Queries Worse Too

Indexes are not free.

Every time you:

```sql
INSERT
UPDATE
DELETE
```

the database may also need to update indexes.

For example:

```text
Table
   ↓
Index 1
Index 2
Index 3
Index 4
```

Too many indexes can mean:

```text
SELECT → potentially faster

INSERT/UPDATE/DELETE → potentially slower
Storage → increased
```

So don't create indexes on every column.

---

# 7. Avoid Functions on Indexed Columns

Suppose:

```sql
CREATE INDEX idx_email
ON employees(email);
```

This is usually index-friendly:

```sql
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

But:

```sql
SELECT *
FROM employees
WHERE LOWER(email) = 'john@gmail.com';
```

may prevent the normal index from being used effectively, depending on the database and available functional indexes.

Prefer storing/searching normalized data appropriately, or use a suitable functional/generated-column index when supported.

---

# 8. Avoid `SELECT *`

Instead of:

```sql
SELECT *
FROM employees
WHERE department_id = 10;
```

prefer:

```sql
SELECT id, name, email
FROM employees
WHERE department_id = 10;
```

Why?

```text
SELECT * 
   ↓
more columns
   ↓
more data transferred/read
   ↓
potentially more I/O
```

This becomes particularly important in Spring Boot APIs because unnecessary DB data can also increase application/network overhead.

---

# 9. Avoid Leading `%` in `LIKE`

This can often use an index:

```sql
WHERE name LIKE 'John%'
```

But this generally cannot efficiently use a normal B-tree index:

```sql
WHERE name LIKE '%John%'
```

Because the database doesn't know where the value starts.

For large-scale substring searching, consider database-specific **full-text/search indexes** instead.

---

# 10. Pagination Optimization

Avoid:

```sql
SELECT *
FROM employees
ORDER BY id
LIMIT 20 OFFSET 1000000;
```

For huge datasets, large `OFFSET` values can become expensive.

A common alternative is **keyset/seek pagination**:

```sql
SELECT *
FROM employees
WHERE id > 1000000
ORDER BY id
LIMIT 20;
```

With an index on `id`, this can be much more efficient.

---

# 11. Query Optimization Checklist

When a query is slow:

```text
1. Identify the slow query
        ↓
2. Run EXPLAIN / EXPLAIN ANALYZE
        ↓
3. Check table scans
        ↓
4. Check indexes
        ↓
5. Check WHERE / JOIN conditions
        ↓
6. Check composite-index column order
        ↓
7. Avoid unnecessary columns
        ↓
8. Check sorting/grouping
        ↓
9. Re-run EXPLAIN
        ↓
10. Benchmark before/after
```

### Most important concepts for interviews

| Concept           | Remember                         |
| ----------------- | -------------------------------- |
| Index             | Faster data lookup               |
| B-tree            | Common index structure           |
| `EXPLAIN`         | See query execution plan         |
| Full table scan   | Often expensive for large tables |
| Composite index   | Index multiple columns           |
| Leftmost prefix   | Column order matters             |
| Too many indexes  | Slow writes + more storage       |
| `SELECT *`        | Avoid unnecessary data           |
| `LIKE '%abc'`     | Normal index often can't help    |
| Keyset pagination | Better for huge offsets          |

### Spring Boot connection

In Spring Boot, you might write:

```java
List<Employee> employees =
    employeeRepository.findByDepartmentId(10);
```

Spring Data JPA generates SQL, but **the database still decides how that SQL is executed**.

So as a full-stack engineer, you need to understand both:

```text
Spring Boot/JPA
      ↓
Generated SQL
      ↓
Database Optimizer
      ↓
Indexes
      ↓
Execution Plan
      ↓
Performance
```

**Key takeaway:** Don't think *"I created an index, therefore the query is fast."* Think **"I created an appropriate index, then verified that the optimizer actually uses it with `EXPLAIN`."**
