## Database Transactions — ACID

A **transaction** is a group of database operations treated as **one unit of work**.

### Banking example

Suppose **A sends ₹1,000 to B**.

We need two operations:

```sql
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;  -- A

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;  -- B
```

These two operations must behave as **one transaction**.

If ₹1,000 is deducted from A but the application crashes before adding it to B, money disappears. Transactions prevent this kind of partial update.

---

# ACID

ACID = **Atomicity + Consistency + Isolation + Durability**

| Property        | Meaning                                              | Banking example                                                       |
| --------------- | ---------------------------------------------------- | --------------------------------------------------------------------- |
| **Atomicity**   | All operations succeed or all are rolled back        | Debit + credit both happen, or neither happens                        |
| **Consistency** | DB moves from one valid state to another valid state | Account balances/rules remain valid                                   |
| **Isolation**   | Concurrent transactions don't incorrectly interfere  | Two transfers shouldn't corrupt the same balance                      |
| **Durability**  | Committed data survives crashes                      | After transfer commits, money remains transferred even if DB restarts |

---

## 1. Atomicity

Think:

> **All or nothing**

```text
BEGIN TRANSACTION

A: -₹1000
B: +₹1000

COMMIT
```

If something fails:

```text
BEGIN TRANSACTION

A: -₹1000
B: ❌ FAILED

ROLLBACK
```

After rollback:

```text
A: original balance
B: original balance
```

The partial change to A is undone.

### SQL

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

If something goes wrong:

```sql
ROLLBACK;
```

---

# 2. Consistency

The transaction must preserve the database's **rules/constraints**.

For example:

```text
A = ₹10,000
B = ₹5,000

Total = ₹15,000
```

Transfer ₹1,000:

```text
A = ₹9,000
B = ₹6,000

Total = ₹15,000
```

The transaction shouldn't leave the database violating constraints such as:

```sql
balance >= 0
```

or:

```sql
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
```

**Important:** Consistency is about maintaining defined database/business rules, not simply "the data looks correct."

---

# 3. Isolation

Imagine two transfers happen at the same time.

```text
Transaction T1: A → B ₹1,000
Transaction T2: A → C ₹2,000
```

Both transactions are accessing A's balance concurrently.

Without proper isolation, one transaction could read/update data based on an incorrect intermediate state.

The database provides **isolation levels** to control this.

Common levels:

```text
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

For MySQL InnoDB, **REPEATABLE READ** is the default isolation level.

You don't need to memorize all the internals initially; understand that:

> Isolation controls how concurrent transactions see each other's changes.

---

# 4. Durability

Once:

```sql
COMMIT;
```

succeeds, the transaction is considered permanently committed.

Even if:

```text
Application crashes
↓
Server restarts
↓
Database restarts
```

the committed transfer should still exist.

Conceptually:

```text
COMMIT
  ↓
Database persists changes
  ↓
Crash
  ↓
Restart
  ↓
Committed data remains
```

# Complete Banking Example

Assume:

```text
Account A = ₹10,000
Account B = ₹5,000
```

Transfer ₹1,000:

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

Result:

```text
A = ₹9,000
B = ₹6,000
```

If the second operation fails:

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

-- Something fails here

ROLLBACK;
```

Result:

```text
A = ₹10,000
B = ₹5,000
```

That's **Atomicity**.

# How this relates to Spring Boot

This is extremely important for your Spring Boot learning.

In Spring, you commonly use:

```java
@Transactional
```

Example:

```java
@Service
public class TransferService {

    @Transactional
    public void transfer(int fromId, int toId, double amount) {

        accountRepository.debit(fromId, amount);

        accountRepository.credit(toId, amount);
    }
}
```

Conceptually Spring does:

```text
@Transactional
      ↓
BEGIN TRANSACTION
      ↓
debit()
      ↓
credit()
      ↓
If everything succeeds → COMMIT
If RuntimeException occurs → ROLLBACK
```

So instead of manually writing:

```sql
START TRANSACTION;
COMMIT;
ROLLBACK;
```

Spring can manage the transaction boundary for you.

### ⭐ Interview takeaway

> **A transaction groups multiple database operations into a single unit of work. ACID guarantees Atomicity, Consistency, Isolation, and Durability. In Spring Boot, `@Transactional` is commonly used to manage transaction boundaries.**

One important next topic after ACID is **`@Transactional` in Spring Boot + rollback rules + propagation**, because that's where database transactions become practical in your backend development.
