# Database Normalization — 1NF, 2NF, 3NF & Schema Design

Since you're moving from **React → Java/Spring Boot**, normalization is important because you'll frequently design **MySQL tables + JPA entities**.

## What is Normalization?

**Normalization = organizing database tables to reduce duplicate data and avoid data problems.**

Main goals:

* Reduce **data duplication**
* Avoid **update anomalies**
* Avoid **insert anomalies**
* Avoid **delete anomalies**
* Keep relationships clear

A common progression is:

```text
Unnormalized
    ↓
1NF
    ↓
2NF
    ↓
3NF
```

For most normal application databases, **3NF is a very useful target**.

---

Note: Anomaly

In database normalization, **anomaly** simply means an **unwanted problem caused by poor table design**, usually because the same data is duplicated.

There are **3 common anomalies**:

### 1. Insert Anomaly

You **cannot insert some information** without unrelated information.

Example:

```text
Student_Course
student_id | student_name | course_id | course_name
-----------|--------------|-----------|-----------
1          | Ravi         | C101      | Java
```

If you want to add a new course **Python**, but no student has enrolled yet, you may not be able to insert it properly.

---

### 2. Update Anomaly

The **same information exists in multiple rows**, so you must update it everywhere.

```text
student_id | student_name | course | instructor
-----------|--------------|--------|-----------
1          | Ravi         | Java   | Kumar
2          | Arun         | Java   | Kumar
3          | Priya        | Java   | Kumar
```

If Kumar's name/details change, you need to update multiple rows.

If you update only one row → **inconsistent data**.

---

### 3. Delete Anomaly

Deleting one piece of information **accidentally removes another useful piece of information**.

```text
student_id | student_name | course
-----------|--------------|--------
1          | Ravi         | Java
2          | Arun         | Python
```

If Ravi is the **only student enrolled in Java** and you delete Ravi's row, you also lose information that the **Java course exists**.

---

### Easy way to remember

```text
Insert  → Can't add data properly
Update  → Same data must be changed multiple places
Delete  → Deleting one thing accidentally deletes another
```

**Normalization helps prevent these anomalies by separating logically different data into appropriate tables.**

---

# Example: Badly Designed Table

Suppose we store orders like this:

| order_id | customer_name | customer_phone | products      |
| -------- | ------------- | -------------- | ------------- |
| 101      | Ravi          | 9876543210     | Laptop, Mouse |
| 102      | Kumar         | 9876543222     | Keyboard      |

Problems:

* `products` contains multiple values.
* Customer information may be repeated across orders.
* Updating customer information requires multiple rows.
* Searching individual products becomes difficult.

Normalization fixes this.

---

# 1NF — First Normal Form

### Rule

A table is in **1NF** when:

1. Each column contains **atomic/single values**
2. No repeating groups or multi-valued columns
3. Each row represents a distinct record

### ❌ Not 1NF

```text
order_id | customer | products
---------|----------|------------------
101      | Ravi     | Laptop, Mouse
```

`products` contains multiple values.

### ✅ 1NF

```text
order_id | customer | product
---------|----------|--------
101      | Ravi     | Laptop
101      | Ravi     | Mouse
```

Each cell contains one value.

### SQL

```sql
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT
);
```

Each row represents one product within an order.

---

# 2NF — Second Normal Form

### Rule

A table must:

1. Already be in **1NF**
2. Have **no partial dependency** on a composite primary key.

This concept is mainly important when the table has a **composite primary key**.

Consider:

```text
order_id | product_id | product_name | quantity
---------|------------|--------------|---------
101      | 1          | Laptop       | 2
101      | 2          | Mouse        | 1
102      | 1          | Laptop       | 1
```

Primary key:

```text
(order_id, product_id)
```

But:

```text
product_name
```

depends only on:

```text
product_id
```

not the entire composite key.

That's a **partial dependency**.

### ❌ Bad design

```text
OrderItems
--------------------------------
order_id
product_id
product_name
quantity
```

### ✅ 2NF

Separate product information:

```text
Products
----------------
product_id
product_name
```

And order-specific information:

```text
OrderItems
----------------
order_id
product_id
quantity
```

Now:

```text
Products
1 → Laptop
2 → Mouse
```

```text
OrderItems
101, 1 → quantity 2
101, 2 → quantity 1
```

### Easy way to remember

> **2NF removes dependency on only part of a composite key.**

---

# 3NF — Third Normal Form

### Rule

A table must:

1. Be in **2NF**
2. Have **no transitive dependency**

Meaning:

> A non-key column should not depend on another non-key column.

### Example

```text
Employee
------------------------------------------------
employee_id | employee_name | dept_id | dept_name
```

Primary key:

```text
employee_id
```

Dependencies:

```text
employee_id → dept_id
dept_id → dept_name
```

Therefore:

```text
employee_id → dept_name
```

indirectly.

That's a **transitive dependency**.

### ❌ Bad design

```text
Employee
----------------------------
employee_id
employee_name
dept_id
dept_name
```

### ✅ 3NF

Separate department information:

```text
Employee
----------------
employee_id
employee_name
dept_id
```

```text
Department
----------------
dept_id
dept_name
```

Relationship:

```text
Employee
   |
   | FK
   ↓
Department
```

# Complete Schema Design Example

Let's design a simple e-commerce database.

### 1. Customer

```sql
CREATE TABLE customers (
    customer_id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL
);
```

### 2. Products

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY AUTO_INCREMENT,
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10,2) NOT NULL
);
```

### 3. Orders

```sql
CREATE TABLE orders (
    order_id INT PRIMARY KEY AUTO_INCREMENT,
    customer_id INT NOT NULL,
    order_date DATE NOT NULL,

    FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);
```

### 4. Order Items

```sql
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT NOT NULL,

    PRIMARY KEY (order_id, product_id),

    FOREIGN KEY (order_id)
        REFERENCES orders(order_id),

    FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);
```

Relationship:

```text
Customer
   |
   | 1:N
   ↓
 Orders
   |
   | 1:N
   ↓
OrderItems
   |
   | N:1
   ↓
Products
```

---

# Why This Design Is Better

Suppose Ravi places 10 orders.

### ❌ Unnormalized

Ravi's information could be repeated 10 times.

### ✅ Normalized

Ravi exists once:

```text
customers
----------------
1 | Ravi | ravi@email.com
```

Orders reference him:

```text
orders
----------------
101 | customer_id=1
102 | customer_id=1
103 | customer_id=1
```

Products also exist once:

```text
products
----------------
1 | Laptop
2 | Mouse
```

Order items simply reference them:

```text
order_items
-------------------------
101 | 1 | 1
101 | 2 | 2
```

This gives you less duplication and cleaner relationships.

---

# 1NF vs 2NF vs 3NF

| Normal Form | Main Problem Removed                    |
| ----------- | --------------------------------------- |
| **1NF**     | Multiple/repeating values in one column |
| **2NF**     | Partial dependency                      |
| **3NF**     | Transitive dependency                   |

### Memory trick

```text
1NF → Atomic values

2NF → Whole key

3NF → Nothing but the key
```

The classic phrase is:

> **"The key, the whole key, and nothing but the key."**

Meaning:

```text
1NF → values are atomic
2NF → columns depend on the WHOLE key
3NF → columns depend ONLY on the key
```

## One Important Real-World Point

**Normalization doesn't mean "split everything into separate tables."**

In real applications, you sometimes deliberately **denormalize** for performance or reporting.

For your Spring Boot + MySQL learning path, understand this order:

```text
Normalization
    ↓
Primary Key / Foreign Key
    ↓
Relationships (1:1, 1:N, N:N)
    ↓
JOINs
    ↓
Indexes
    ↓
JPA Entity Relationships
    ↓
Spring Data JPA
```

For interviews, be especially comfortable explaining **why `OrderItems` needs a composite key and why `Product` information should not be duplicated inside it**.
