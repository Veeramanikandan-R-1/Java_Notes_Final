## Database — Query Optimization

Since you already know MySQL, focus on **how the database executes your query and how you identify why a query is slow**.

---

# 1. What is Query Optimization?

Suppose you write:

```sql
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

The database has multiple ways to find the row.

### Approach 1 — Scan every row

```text
Row 1 → check email
Row 2 → check email
Row 3 → check email
...
Row 1,000,000 → check email
```

This is a **Full Table Scan**.

### Approach 2 — Use an index

```text
Index
  ↓
john@gmail.com
  ↓
Employee row
```

Much faster when the index is appropriate.

The database's **query optimizer** decides how to execute your SQL.

---

# 2. Execution Plan

An **execution plan** is the database's plan for executing your query.

It tells you things such as:

* Which table is accessed
* Whether an index is used
* How many rows are scanned
* Which join algorithm is used
* Estimated execution cost
* Sorting/grouping operations

Think of it as:

```text
SQL Query
    ↓
Query Optimizer
    ↓
Execution Plan
    ↓
Database executes plan
    ↓
Result
```

---

# 3. MySQL — `EXPLAIN`

Use:

```sql
EXPLAIN
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

Example output conceptually:

```text
type   possible_keys   key       rows
-----  --------------  --------  ----
ALL    NULL            NULL      100000
```

This is suspicious because:

```text
type = ALL
```

usually means **full table scan**.

---

# 4. Create an Index

Suppose:

```sql
CREATE INDEX idx_employee_email
ON employees(email);
```

Now:

```sql
EXPLAIN
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

You may see something like:

```text
type   possible_keys       key                  rows
-----  ------------------  -------------------  ----
const  idx_employee_email  idx_employee_email   1
```

Now MySQL can use the index.

### Important

Don't assume:

> "If I create an index, MySQL will always use it."

The optimizer decides whether the index is beneficial.

---

# 5. PostgreSQL — `EXPLAIN`

If you're using PostgreSQL:

```sql
EXPLAIN
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

You might see:

```text
Index Scan using idx_employee_email on employees
```

For actual execution statistics:

```sql
EXPLAIN ANALYZE
SELECT *
FROM employees
WHERE email = 'john@gmail.com';
```

### Difference

```text
EXPLAIN
    ↓
Shows the planned execution

EXPLAIN ANALYZE
    ↓
Actually executes the query
    +
Shows actual execution statistics
```

Be careful with `EXPLAIN ANALYZE` on `UPDATE`/`DELETE` because it actually executes the statement.

---

# 6. Important Execution Plan Concepts

When reading an execution plan, focus on these first:

### 1. Full Table Scan

```text
MySQL: ALL
PostgreSQL: Seq Scan
```

The database examines many/all rows.

Not automatically bad—if the table is tiny, a sequential scan can actually be the fastest choice.

---

### 2. Index Scan

```text
Index
  ↓
Matching rows
```

Usually useful when the query selects a relatively small portion of a large table.

---

### 3. Rows examined

Imagine:

```text
rows examined = 1,000,000
rows returned = 1
```

That's a strong indication that the query may need optimization.

---

### 4. Join strategy

For:

```sql
SELECT *
FROM employees e
JOIN departments d
    ON e.department_id = d.id;
```

The database needs to determine **how to join the tables**.

Depending on the database and situation, it may use algorithms such as:

```text
Nested Loop
Hash Join
Merge Join
```

You don't need to memorize these yet. The important concept is:

> The optimizer chooses a strategy based on statistics, indexes, estimated rows, and costs.

---

# 7. Performance Problem Example

Suppose:

```sql
SELECT *
FROM employees
WHERE YEAR(joining_date) = 2025;
```

You have an index:

```sql
CREATE INDEX idx_joining_date
ON employees(joining_date);
```

But applying:

```sql
YEAR(joining_date)
```

to every row can prevent efficient use of that index.

A range condition is often better:

```sql
SELECT *
FROM employees
WHERE joining_date >= '2025-01-01'
  AND joining_date < '2026-01-01';
```

This gives the optimizer a much better opportunity to use the date index.

---

# 8. Another Common Problem — `SELECT *`

Instead of:

```sql
SELECT *
FROM employees
WHERE department_id = 10;
```

if you only need:

```text
name
email
```

use:

```sql
SELECT name, email
FROM employees
WHERE department_id = 10;
```

Benefits:

* Less data read
* Less network transfer
* Less memory usage
* Potentially better index-only/covering access depending on the database and index

---

# 9. Performance Notes

### ✅ Index columns used frequently for filtering

```sql
WHERE email = ?
WHERE employee_id = ?
WHERE department_id = ?
```

But don't blindly index every column.

Indexes also:

* Consume storage
* Increase INSERT/UPDATE/DELETE cost
* Require maintenance

---

### ✅ Avoid unnecessary functions on indexed columns

Prefer:

```sql
WHERE joining_date >= '2025-01-01'
```

over unnecessarily wrapping the column in a function.

---

### ✅ Avoid unnecessary data

Instead of:

```sql
SELECT *
```

select only what you need.

---

### ✅ Always check the execution plan

Don't optimize based purely on intuition.

Use:

```sql
EXPLAIN ...
```

and, where appropriate:

```sql
EXPLAIN ANALYZE ...
```

---

### ✅ Keep statistics up to date

The optimizer relies on statistics to estimate:

```text
How many rows will match?
Which index is useful?
Which join strategy is cheaper?
```

Outdated statistics can lead to poor plans.

---

# 10. The Most Important Mental Model

As a backend engineer, remember:

```text
Slow Query
    ↓
EXPLAIN / EXPLAIN ANALYZE
    ↓
Understand execution plan
    ↓
Find bottleneck
    ↓
Possible solutions
    ├── Better index
    ├── Rewrite query
    ├── Reduce rows/data
    ├── Improve JOIN
    ├── Update statistics
    └── Schema/design change
    ↓
Run EXPLAIN again
    ↓
Compare performance
```

### Interview definition

> **Query optimization is the process of improving a SQL query or database design so that the database can execute the query efficiently, typically by analyzing its execution plan, reducing unnecessary work, and choosing appropriate indexes and query structures.**

For your Spring Boot path, this becomes especially important when you reach **Spring Data JPA → Hibernate → generated SQL → slow API → database optimization**.
