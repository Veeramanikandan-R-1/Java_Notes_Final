# Spring Boot — DTO Pattern: Request & Response DTOs

## 1. What is a DTO?

DTO (Data Transfer Object) is a Java class used to transfer data between the client (React) and the Spring Boot backend.

Instead of exposing your database entity directly through an API, you create separate DTOs for incoming requests and outgoing responses.

Think of it like this:

* Request DTO: Data received from React.

* Entity: Data stored in the database.

* Response DTO: Data returned to React.

React frontend

Sends JSON request

Request DTO

Receives and validates input

Service → Entity → Repository

Business logic and database operations

Response DTO

Returns only the required fields

React frontend

Receives JSON response

### Why use DTOs?

* Security: Avoid exposing passwords and internal database fields.

* Separation of concerns: API structure can differ from the database structure.

* Validation: Validate incoming data using annotations.

* Maintainability: Change entities without necessarily changing API responses.

## 2. Complete working implementation

Example: A React application creates a user and receives user details, excluding the password.

Assume you have a Spring Boot project with Spring Web and Validation dependencies.

### Project structure

```
src/main/java/com/example/demo/
├── DemoApplication.java
├── controller/
│   └── UserController.java
├── dto/
│   ├── UserRequestDTO.java
│   └── UserResponseDTO.java
├── entity/
│   └── User.java
└── service/
    └── UserService.java
```

### Step 1: Add dependencies

In `pom.xml`, ensure Spring Web and Validation are included. Spring Boot's parent or dependency management supplies their versions.

XML

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

### Step 2: Create the request DTO

`dto/UserRequestDTO.java`

Java

```
package com.example.demo.dto;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public class UserRequestDTO {

    @NotBlank(message = "Name is required")
    private String name;

    @Email(message = "Invalid email format")
    @NotBlank(message = "Email is required")
    private String email;

    @NotBlank(message = "Password is required")
    @Size(min = 8, message = "Password must have at least 8 characters")
    private String password;

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }

    public String getPassword() {
        return password;
    }

    public void setPassword(String password) {
        this.password = password;
    }
}
```

Important: `@Valid` in the controller triggers these validation rules. The password is accepted in the request, but we won't return it in the response.

### Step 3: Create the response DTO

`dto/UserResponseDTO.java`

Java

```
package com.example.demo.dto;

public class UserResponseDTO {

    private Long id;
    private String name;
    private String email;

    public UserResponseDTO(Long id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }
}
```

Notice that the response DTO has no password field. This prevents the password from being serialized into the API response.

### Step 4: Create the entity

`entity/User.java`

Java

```
package com.example.demo.entity;

public class User {

    private Long id;
    private String name;
    private String email;
    private String password;

    public User(Long id, String name, String email, String password) {
        this.id = id;
        this.name = name;
        this.email = email;
        this.password = password;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }

    public String getPassword() {
        return password;
    }
}
```

For this example, the entity is a plain Java class and data is stored in memory. In a database-backed application, you would normally use JPA annotations such as `@Entity` and `@Id`.

### Step 5: Create the service

`service/UserService.java`

Java

```
package com.example.demo.service;

import com.example.demo.dto.UserRequestDTO;
import com.example.demo.dto.UserResponseDTO;
import com.example.demo.entity.User;
import org.springframework.stereotype.Service;

import java.util.concurrent.atomic.AtomicLong;

@Service
public class UserService {

    private final AtomicLong idGenerator = new AtomicLong();

    public UserResponseDTO createUser(UserRequestDTO request) {

        // Request DTO -> Entity
        User user = new User(
            idGenerator.incrementAndGet(),
            request.getName(),
            request.getEmail(),
            request.getPassword()
        );

        // Entity -> Response DTO
        return new UserResponseDTO(
            user.getId(),
            user.getName(),
            user.getEmail()
        );
    }
}
```

In a real application, hash the password before storing it, and persist the entity using a repository. This demonstration does neither.

### Step 6: Create the controller

`controller/UserController.java`

Java

```
package com.example.demo.controller;

import com.example.demo.dto.UserRequestDTO;
import com.example.demo.dto.UserResponseDTO;
import com.example.demo.service.UserService;

import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public UserResponseDTO createUser(
            @Valid @RequestBody UserRequestDTO request) {

        return userService.createUser(request);
    }
}
```

* `@RequestBody` converts incoming JSON into `UserRequestDTO`.

* `@Valid` checks the validation annotations.

* `@ResponseStatus(HttpStatus.CREATED)` returns HTTP `201 Created`.

* Spring automatically serializes the returned DTO into JSON.

### Step 7: Main application class

`DemoApplication.java`

Java

```
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

## 3. Test the API

Run your application:

Bash

```
mvn spring-boot:run
```

Use Postman or send a request from React.

Request

* Method: `POST`

* URL: `http://localhost:8080/api/users`

* Header: `Content-Type: application/json`

JSON

```
{
  "name": "Arun",
  "email": "arun@example.com",
  "password": "Secure123"
}
```

Response — HTTP 201 Created

JSON

```
{
  "id": 1,
  "name": "Arun",
  "email": "arun@example.com"
}
```

Notice that `password` is absent from the response.

If you send an invalid email or a password shorter than eight characters, validation fails and Spring Boot normally returns HTTP `400 Bad Request`.

## 4. How the DTO flow works

| Layer      | Responsibility                                            |
| ---------- | --------------------------------------------------------- |
| Controller | Receives `UserRequestDTO`                                 |
| Service    | Converts request DTO to entity and entity to response DTO |
| Repository | Saves or retrieves entities from the database             |
| Response   | Returns `UserResponseDTO` to React                        |

## 5. Interview points

Q1. Why not return the entity directly?

To prevent exposing sensitive fields, decouple API contracts from database structure, and control which fields the client receives.

Q2. What is the difference between request and response DTOs?

* Request DTO defines what the client is allowed to send.

* Response DTO defines what the client is allowed to receive.

Q3. Where should DTO conversion happen?

Usually in the service layer or a dedicated mapper class. For larger projects, tools such as MapStruct can reduce repetitive mapping code.

Q4. Are DTOs database entities?

No. A DTO transfers data; an entity represents persisted domain data. A DTO does not require JPA annotations.

Remember this flow: `Request JSON → Request DTO → Service → Entity → Response DTO → Response JSON`.
