Instead of using the default single user configured in `application.properties`, you can configure multiple users using `InMemoryUserDetailsManager`.

### **1. SecurityConfig.java**

```
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public UserDetailsService userDetailsService() {

        UserDetails user1 = User.builder()
                .username("admin")
                .password("{noop}admin123")
                .roles("ADMIN")
                .build();

        UserDetails user2 = User.builder()
                .username("user")
                .password("{noop}user123")
                .roles("USER")
                .build();

        UserDetails user3 = User.builder()
                .username("manager")
                .password("{noop}manager123")
                .roles("MANAGER")
                .build();

        return new InMemoryUserDetailsManager(user1, user2, user3);
    }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {

        http
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .requestMatchers("/user/**").hasAnyRole("USER", "ADMIN")
                .anyRequest().authenticated()
            )
            .httpBasic(Customizer.withDefaults());

        return http.build();
    }
}
```

### **2. Understanding the configuration**

| Method                         | Purpose                         |
| ------------------------------ | ------------------------------- |
| `User.builder()`               | Creates a user                  |
| `username()`                   | Sets username                   |
| `password()`                   | Sets password                   |
| `roles()`                      | Assigns roles                   |
| `InMemoryUserDetailsManager()` | Stores multiple users in memory |
| `hasRole()`                    | Restricts access based on role  |
| `hasAnyRole()`                 | Allows any matching role        |

`{noop}` means the password is stored without encoding. Use a `PasswordEncoder` such as BCrypt for real applications.

### **3. Test credentials**

| Username | Password   | Role    |
| -------- | ---------- | ------- |
| admin    | admin123   | ADMIN   |
| user     | user123    | USER    |
| manager  | manager123 | MANAGER |

### **Important**

Spring Security will use this `UserDetailsService` instead of the default generated user.

For production applications, store users in a database and authenticate them using a database-backed `UserDetailsService`.

---

Notes:

`{noop}` means **No Operation Password Encoder**.

It tells Spring Security that the password is stored as plain text, without hashing or encryption.

```
.password("{noop}admin123")
```

- `{noop}` – Password encoding strategy.
- `admin123` – Actual password.

### **Other common password encoders**

| Encoder    | Purpose                           |
| ---------- | --------------------------------- |
| `{noop}`   | No password encoding (plain text) |
| `{bcrypt}` | BCrypt password hashing           |
| `{pbkdf2}` | PBKDF2 password hashing           |
| `{scrypt}` | SCrypt password hashing           |
| `{argon2}` | Argon2 password hashing           |

**Recommended for real applications:** BCrypt.

```
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

Then encode passwords before storing them:

```
.password(passwordEncoder().encode("admin123"))
```

**Remember:** `{noop}` is suitable only for learning and local testing, not production.
