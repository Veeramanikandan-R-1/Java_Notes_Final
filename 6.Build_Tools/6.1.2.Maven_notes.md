## Java Application Build and Unit Testing — Corrected Notes

Your diagram represents the Java build process, but a few steps need correction.

### 1. Correct execution and build flow

Step 1: Source code

- Write Java code in `.java` files.
- Example: `Calculator.java`

Step 2: Compile

- The Java compiler (`javac`) converts `.java` files into `.class` bytecode files.
- Compilation does not automatically run unit tests.

Step 3: Write and run unit tests

- Write test cases using JUnit 5.
- Test the compiled application code by checking expected and actual results.
- In a Maven project, run tests using `mvn test`.

Step 4: Build the application

- Maven or Gradle compiles the source code, compiles test code, runs tests, and packages the application.
- Tests must pass for the build to succeed when the build is configured to fail on test errors.

Step 5: Package the application

- JAR (`.jar`): Commonly used for Java libraries and executable Spring Boot applications.
- WAR (`.war`): Commonly used for deployment to a compatible application server.

### 2. Important correction

Unit testing is not a conversion step between bytecode and the application package. It is a separate verification step performed during the build process.

For a Maven project, use:

```
mvn test
```

To build and package the application after running tests:

```
mvn package
```

Maven typically creates the resulting JAR or WAR inside the `target/` directory.

Remember: `.java` → `.class` → unit tests verify behavior → build and package → `.jar` or `.war`.

## JAR vs WAR in Java

1\. JAR (Java Archive)

- Packages compiled Java classes, libraries, and resources into a single `.jar` file.
- Used for Java applications and libraries.
- Spring Boot applications commonly use executable JAR files with an embedded server such as Tomcat.
- Run using: `java -jar app.jar`

2\. WAR (Web Application Archive)

- Packages a Java web application into a `.war` file.
- Commonly deployed to an external servlet container or application server, such as Tomcat.
- Often used when the server manages the application deployment.

### Difference

| Feature    | JAR                                 | WAR                                     |
| ---------- | ----------------------------------- | --------------------------------------- |
| Full form  | Java Archive                        | Web Application Archive                 |
| Extension  | `.jar`                              | `.war`                                  |
| Common use | Java apps and libraries             | Java web applications                   |
| Deployment | Can run independently if executable | Commonly deployed to an external server |

Remember: Spring Boot supports both JAR and WAR, but JAR is the default and commonly preferred choice for new Spring Boot applications.

## Maven Java Application vs Web Application

| Feature         | Java Application                                                   | Web Application                                 |
| --------------- | ------------------------------------------------------------------ | ----------------------------------------------- |
| Purpose         | Standalone Java program                                            | Web-based application                           |
| Entry point     | Usually `main()` method                                            | Web server handles HTTP requests                |
| Packaging       | Usually `.jar`                                                     | Usually `.war` (can also be `.jar`)             |
| Execution       | `java -jar app.jar` or `mvn exec:java` with suitable configuration | `mvn spring-boot:run` or deploy to a web server |
| Examples        | CLI tool, file-processing utility                                  | REST API, Spring Boot backend                   |
| Maven archetype | `maven-archetype-quickstart`                                       | `maven-archetype-webapp`                        |

Important: Maven is the build tool for both types. The difference is the application's purpose and structure, not Maven itself.

For your Spring Boot REST API, you can create a Maven project with `spring-boot-starter-web` and package it as an executable JAR.

## Maven Commands to Create Java and Web Projects

### 1. Create a Java application

Using Maven's quickstart archetype:

```
mvn archetype:generate -DgroupId=com.example -DartifactId=my-java-app -DarchetypeArtifactId=maven-archetype-quickstart -DinteractiveMode=false
```

- Creates a basic Java project with a `main()` method and a test class.
- Default packaging: `jar`.

### 2. Create a Java web application

Using Maven's webapp archetype:

```
mvn archetype:generate -DgroupId=com.example -DartifactId=my-web-app -DarchetypeArtifactId=maven-archetype-webapp -DinteractiveMode=false
```

- Creates a basic Java web application structure.
- Default packaging: `war`.

### 3. Create a Spring Boot web application (recommended for you)

For a Spring Boot REST API, use Spring Initializr:

```
https://start.spring.io/
```

Choose Maven, Java, and Spring Web, then generate and extract the project.

Or, if you have Spring Boot CLI installed:

```
spring init --build=maven --java-version=21 --dependencies=web my-spring-app
```

### Quick comparison

| Project                  | Command/tool                 | Packaging              |
| ------------------------ | ---------------------------- | ---------------------- |
| Java application         | `maven-archetype-quickstart` | JAR                    |
| Traditional Java web app | `maven-archetype-webapp`     | WAR                    |
| Spring Boot web app      | Spring Initializr            | Usually executable JAR |

Note: Maven archetypes create project templates; they do not automatically make a project a Spring Boot application. For your React + Spring Boot full-stack goal, use Spring Initializr with Spring Web.

## Types of Maven Repositories

Maven has 3 main types of repositories.

### 1. Local Repository

- Stored on your computer.
- Keeps downloaded dependencies and locally installed project artifacts.
- Default location on Windows: `C:\Users\<username>\.m2\repository`

Command to install your project artifact locally:

```
mvn install
```

### 2. Central Repository

- A public repository containing Java libraries and dependencies.
- Maven downloads dependencies from it when they are not available locally.
- Example: JUnit, Spring Boot libraries.

Website: [Maven Central Repository](https://central.sonatype.com/?utm_source=chatgpt.com)

### 3. Remote Repository

- A repository hosted on a remote server, such as a company's private artifact repository.
- Can contain public or private libraries.
- Examples: Nexus Repository and JFrog Artifactory.

## How they work together

1. Maven checks the local repository for a required dependency.
2. If it is missing, Maven checks configured remote repositories, commonly Maven Central.
3. The downloaded dependency is stored in the local repository for future use.

Important: Maven Central is itself a remote repository. In beginner explanations, “Central Repository” and “Remote Repository” are often listed separately to distinguish the public default repository from other remote repositories.

## Effective POM in Maven (Short Notes)

Effective POM is the final `pom.xml` that Maven uses after combining your project's `pom.xml` with its parent POMs and Maven's default configurations.

Why is it useful?

- Shows inherited dependencies, plugins, and configurations.
- Helps understand where a configuration comes from.
- Useful for debugging Maven build issues.

Command to view Effective POM:

```
mvn help:effective-pom
```

Save the output to a file:

```
mvn help:effective-pom -Doutput=effective-pom.xml
```

Example: If your project's `pom.xml` inherits from Spring Boot's parent POM, the Effective POM includes configurations inherited from that parent.

Remember: `pom.xml` is your project's configuration file; the Effective POM is the complete, resolved configuration Maven uses.

## Maven Build Lifecycle (Short Notes)

The Maven Build Lifecycle is a sequence of steps Maven follows to build, test, package, and deploy a Java application.

### 1. Three Build Lifecycles

| Lifecycle | Purpose                                                |
| --------- | ------------------------------------------------------ |
| `default` | Compiles, tests, packages, and deploys the application |
| `clean`   | Removes previously generated build files               |
| `site`    | Generates project documentation                        |

### 2. Important Phases in the Default Lifecycle

| Phase      | Purpose                                          |
| ---------- | ------------------------------------------------ |
| `validate` | Checks project configuration                     |
| `compile`  | Compiles source code                             |
| `test`     | Runs unit tests                                  |
| `package`  | Creates JAR/WAR file                             |
| `verify`   | Runs additional validation checks                |
| `install`  | Saves the artifact in the local Maven repository |
| `deploy`   | Publishes the artifact to a remote repository    |

Execution order:

`validate → compile → test → package → verify → install → deploy`

Maven executes all preceding phases when you specify a later phase.

### 3. Common Commands

```
mvn clean
mvn compile
mvn test
mvn package
mvn verify
mvn install
mvn deploy
```

Run a clean build and install the artifact:

```
mvn clean install
```

This removes old build output, builds the project, runs tests, packages the application, and installs the artifact locally.

Remember: Maven phases execute in order. For example, `mvn package` automatically runs validation, compilation, and tests before packaging (unless configured otherwise).
