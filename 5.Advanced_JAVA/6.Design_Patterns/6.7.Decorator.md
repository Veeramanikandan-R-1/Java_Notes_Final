## Design Pattern: Decorator

### 1. What is Decorator Pattern?

**Decorator is a Structural Design Pattern**.

It allows you to **add new behavior/functionality to an existing object dynamically without modifying its original class**.

Think of it like adding layers:

```text
Basic Coffee
     ↓
+ Milk
     ↓
+ Sugar
     ↓
+ Whipped Cream
```

Each decorator **wraps** the previous object and adds something extra.

### 2. When to use it?

Use Decorator when:

* You want to add features dynamically.
* You don't want to modify the original class.
* You want to avoid creating many subclasses.

For example, instead of:

```text
Coffee
CoffeeWithMilk
CoffeeWithSugar
CoffeeWithMilkAndSugar
CoffeeWithMilkSugarCream
...
```

you can dynamically combine decorators.

---

# 3. Structure

The main idea is:

```text
             Component
                ↑
        ┌───────┴────────┐
   ConcreteComponent   Decorator
                         ↑
                 ConcreteDecorator
```

The important part:

> **Decorator implements the same interface as the original object and contains a reference to that interface.**

---

# 4. Full Working Java Example

```java
interface Coffee {

    String getDescription();

    double getCost();
}
```

### Concrete Component

```java
class SimpleCoffee implements Coffee {

    @Override
    public String getDescription() {
        return "Simple Coffee";
    }

    @Override
    public double getCost() {
        return 100;
    }
}
```

### Base Decorator

```java
class CoffeeDecorator implements Coffee {

    protected Coffee coffee;

    public CoffeeDecorator(Coffee coffee) {
        this.coffee = coffee;
    }

    @Override
    public String getDescription() {
        return coffee.getDescription();
    }

    @Override
    public double getCost() {
        return coffee.getCost();
    }
}
```

### Concrete Decorator 1

```java
class MilkDecorator extends CoffeeDecorator {

    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public String getDescription() {
        return coffee.getDescription() + ", Milk";
    }

    @Override
    public double getCost() {
        return coffee.getCost() + 20;
    }
}
```

### Concrete Decorator 2

```java
class SugarDecorator extends CoffeeDecorator {

    public SugarDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public String getDescription() {
        return coffee.getDescription() + ", Sugar";
    }

    @Override
    public double getCost() {
        return coffee.getCost() + 10;
    }
}
```

### Main

```java
public class Main {

    public static void main(String[] args) {

        Coffee coffee = new SimpleCoffee();

        coffee = new MilkDecorator(coffee);

        coffee = new SugarDecorator(coffee);

        System.out.println(coffee.getDescription());
        System.out.println("Cost: ₹" + coffee.getCost());
    }
}
```

### Output

```text
Simple Coffee, Milk, Sugar
Cost: ₹130.0
```

# 5. Understand the Flow

This line:

```java
Coffee coffee = new SimpleCoffee();
```

```text
SimpleCoffee
Cost = 100
```

Then:

```java
coffee = new MilkDecorator(coffee);
```

Now:

```text
MilkDecorator
      ↓
SimpleCoffee
```

Cost:

```text
100 + 20 = 120
```

Then:

```java
coffee = new SugarDecorator(coffee);
```

Now:

```text
SugarDecorator
      ↓
MilkDecorator
      ↓
SimpleCoffee
```

Cost:

```text
100 + 20 + 10 = 130
```

This is the core idea of Decorator:

> **Wrap an object with another object to add behavior.**

---

# 6. Most Important Line

You should understand this:

```java
class CoffeeDecorator implements Coffee {

    protected Coffee coffee;

    public CoffeeDecorator(Coffee coffee) {
        this.coffee = coffee;
    }
}
```

The decorator:

1. **implements the same interface** → `Coffee`
2. **holds another Coffee object**
3. delegates existing behavior
4. adds its own behavior

That's why this works:

```java
new SugarDecorator(
    new MilkDecorator(
        new SimpleCoffee()
    )
);
```

---

# 7. Why not inheritance?

Without Decorator, you might create:

```text
SimpleCoffee
   ↓
MilkCoffee
   ↓
MilkSugarCoffee
   ↓
MilkSugarCreamCoffee
```

As combinations increase, the number of classes becomes difficult to manage.

Decorator uses **composition instead of creating subclasses for every combination**.

```text
Coffee
  ↑
Decorator
  ↑
MilkDecorator
  ↑
SugarDecorator
```

Features can be combined dynamically.

# 8. Decorator vs Adapter

This is important for interviews.

| Pattern       | Purpose                                     |
| ------------- | ------------------------------------------- |
| **Adapter**   | Makes incompatible interfaces work together |
| **Decorator** | Adds new behavior to an existing object     |
| **Strategy**  | Changes/selects an algorithm                |
| **Factory**   | Creates objects                             |
| **Builder**   | Builds complex objects                      |
| **Observer**  | Notifies multiple subscribers               |

### Easy memory trick

```text
Adapter   → "Make it compatible"
Decorator → "Add more behavior"
Strategy  → "Choose behavior"
Factory   → "Create object"
Builder   → "Build object"
Observer  → "Notify objects"
```

### Spring Boot relevance

Decorator is useful when you need to add responsibilities around an existing service, such as:

```text
Service
  ↓
Logging Decorator
  ↓
Caching Decorator
  ↓
Actual Service
```

In Spring, **AOP/proxies/decorating behavior around beans** use closely related concepts.
