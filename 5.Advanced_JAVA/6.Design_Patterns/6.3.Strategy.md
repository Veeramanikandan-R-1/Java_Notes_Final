# Design Pattern: Strategy

**Strategy Pattern** is a **Behavioral Design Pattern**.

It is used when you have **multiple ways/algorithms to perform the same operation** and want to choose the behavior dynamically.

### Simple idea

Instead of:

```java
if (type.equals("UPI")) {
    // UPI logic
} else if (type.equals("CARD")) {
    // Card logic
} else if (type.equals("NETBANKING")) {
    // Net banking logic
}
```

we separate each algorithm into its own class.

```text
PaymentService
      ↓
  PaymentStrategy
      ↓
 ┌────┴─────────┬──────────────┐
UPIPayment   CardPayment   NetBankingPayment
```

---

## 1. Create the Strategy interface

```java
interface PaymentStrategy {

    void pay(double amount);
}
```

This defines the common behavior.

---

## 2. Create different strategies

```java
class UPIPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using UPI");
    }
}
```

```java
class CardPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using Card");
    }
}
```

```java
class NetBankingPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using Net Banking");
    }
}
```

Each class contains **one specific algorithm/behavior**.

---

## 3. Create the Context

The **Context** uses a strategy but doesn't need to know how the strategy works.

```java
class PaymentService {

    private PaymentStrategy strategy;

    public PaymentService(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void makePayment(double amount) {
        strategy.pay(amount);
    }
}
```

---

## 4. Complete working example

```java
interface PaymentStrategy {

    void pay(double amount);
}

class UPIPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using UPI");
    }
}

class CardPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using Card");
    }
}

class NetBankingPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using Net Banking");
    }
}

class PaymentService {

    private PaymentStrategy strategy;

    public PaymentService(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void makePayment(double amount) {
        strategy.pay(amount);
    }
}

public class Main {

    public static void main(String[] args) {

        PaymentStrategy strategy = new UPIPayment();

        PaymentService service = new PaymentService(strategy);

        service.makePayment(1000);

        // Change strategy dynamically
        strategy = new CardPayment();

        service = new PaymentService(strategy);

        service.makePayment(2000);
    }
}
```

### Output

```text
Paid ₹1000.0 using UPI
Paid ₹2000.0 using Card
```

# 5. Why Strategy Pattern?

### Without Strategy

```java
class PaymentService {

    public void pay(String type, double amount) {

        if (type.equals("UPI")) {
            // UPI logic
        } else if (type.equals("CARD")) {
            // Card logic
        } else if (type.equals("NETBANKING")) {
            // Net banking logic
        }
    }
}
```

Problems:

* Large `if/else` or `switch`
* Difficult to maintain
* Adding a new payment method requires modifying existing code
* Violates **Open/Closed Principle**

---

### With Strategy

```java
PaymentStrategy strategy = new UPIPayment();

PaymentService service =
        new PaymentService(strategy);

service.makePayment(1000);
```

Now adding:

```java
class WalletPayment implements PaymentStrategy {
    // Wallet logic
}
```

doesn't require changing `PaymentService`.

---

# 6. Very important: Strategy vs Factory

Since you're learning both, don't confuse them.

### Factory

**Factory answers:**

> "Which object should I create?"

```java
PaymentStrategy strategy =
        PaymentFactory.create("UPI");
```

### Strategy

**Strategy answers:**

> "Which behavior/algorithm should I use?"

```java
PaymentService service =
        new PaymentService(new UPIPayment());
```

So:

```text
Factory  → Object creation
Strategy → Object behavior/algorithm
```

They can also be used **together**.

# 7. Real Spring Boot Connection ⭐

Strategy is very common in Spring Boot.

You might have:

```java
interface NotificationStrategy {
    void send(String message);
}
```

Implementations:

```java
@Component
class EmailNotification implements NotificationStrategy {
    public void send(String message) {
        // email
    }
}
```

```java
@Component
class SmsNotification implements NotificationStrategy {
    public void send(String message) {
        // SMS
    }
}
```

Then Spring manages these implementations and injects them.

This is one reason **interfaces + dependency injection + Strategy** are important concepts for your Spring Boot learning.

---

## Interview Answer

> **Strategy Pattern is a behavioral design pattern that encapsulates multiple interchangeable algorithms or behaviors behind a common interface and allows the behavior to be selected or changed at runtime.**

### Remember

```text
Strategy
   ↓
Same task
   ↓
Multiple algorithms/behaviors
   ↓
Each behavior → separate class
   ↓
Common interface
   ↓
Choose behavior dynamically
```

**Example:** Payment → UPI / Card / NetBanking,
**Sorting:** QuickSort / MergeSort,
**Notification:** Email / SMS / Push.
