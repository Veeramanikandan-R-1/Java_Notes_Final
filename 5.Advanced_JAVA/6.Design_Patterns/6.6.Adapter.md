# Design Pattern: Adapter

**Adapter Pattern** is a **Structural Design Pattern**.

Its purpose is simple:

> **Make two incompatible interfaces work together without changing their existing code.**

Think of it like a **mobile charger adapter**:

```text
Wall Socket
     ↓
  Adapter
     ↓
Mobile Charger
```

The socket and charger have different interfaces, but the adapter makes them compatible.

---

# 1. Java Example

Suppose our application expects:

```java
interface PaymentProcessor {
    void pay(double amount);
}
```

Our application wants to use:

```java
PaymentProcessor processor;
processor.pay(1000);
```

But we have an existing third-party class:

```java
class OldPaymentGateway {

    public void makePayment(double amount) {
        System.out.println("Payment done: ₹" + amount);
    }
}
```

Problem:

```text
Our application expects:
pay()

Existing gateway provides:
makePayment()
```

The interfaces don't match.

We **cannot change** `OldPaymentGateway` because it may be third-party/legacy code.

So we create an **Adapter**.

---

# 2. Adapter

```java
class PaymentAdapter implements PaymentProcessor {

    private final OldPaymentGateway gateway;

    public PaymentAdapter(OldPaymentGateway gateway) {
        this.gateway = gateway;
    }

    @Override
    public void pay(double amount) {
        gateway.makePayment(amount);
    }
}
```

The Adapter implements the interface our application expects and internally calls the existing method.

---

# 3. Complete Working Example

```java
interface PaymentProcessor {

    void pay(double amount);
}

// Existing / third-party class
class OldPaymentGateway {

    public void makePayment(double amount) {
        System.out.println("Payment done: ₹" + amount);
    }
}

// Adapter
class PaymentAdapter implements PaymentProcessor {

    private final OldPaymentGateway gateway;

    public PaymentAdapter(OldPaymentGateway gateway) {
        this.gateway = gateway;
    }

    @Override
    public void pay(double amount) {
        gateway.makePayment(amount);
    }
}

// Client
public class Main {

    public static void main(String[] args) {

        OldPaymentGateway oldGateway =
                new OldPaymentGateway();

        PaymentProcessor processor =
                new PaymentAdapter(oldGateway);

        processor.pay(1000);
    }
}
```

### Output

```text
Payment done: ₹1000.0
```

---

# 4. Understand the Flow ⭐

The important part is:

```java
PaymentProcessor processor =
        new PaymentAdapter(oldGateway);
```

The client thinks it is working with:

```text
PaymentProcessor
      ↓
    pay()
```

But internally:

```text
Client
  ↓
PaymentProcessor
  ↓
PaymentAdapter
  ↓
OldPaymentGateway
  ↓
makePayment()
```

The Adapter translates:

```text
pay()
  ↓
makePayment()
```

---

# 5. Why not directly use `OldPaymentGateway`?

You could do:

```java
OldPaymentGateway gateway =
        new OldPaymentGateway();

gateway.makePayment(1000);
```

But now your application is directly dependent on the third-party class.

If tomorrow you replace the payment gateway:

```text
OldPaymentGateway
        ↓
NewPaymentGateway
```

you may have to change many parts of your application.

With Adapter:

```text
Application
    ↓
PaymentProcessor interface
    ↓
Adapter
    ↓
Third-party implementation
```

The application remains dependent on **your interface**, not the external API.

---

# 6. Adapter vs Strategy ⭐

Since you just learned Strategy, this distinction is important.

### Strategy

You have multiple implementations of the **same interface**:

```text
PaymentProcessor
     ↓
 ┌───┼────┐
 ↓   ↓    ↓
UPI Card Wallet
```

You choose **which behavior/algorithm to use**.

### Adapter

You have an **incompatible existing interface**:

```text
Your Interface
     ↓
  Adapter
     ↓
Existing/Third-party Interface
```

You make incompatible interfaces work together.

### Easy memory trick

```text
Strategy → Different ways to do something

Adapter  → Make existing things compatible
```

---

# 7. Adapter vs Factory

Also remember:

```text
Factory
   ↓
Creates the appropriate object

Adapter
   ↓
Makes an existing object compatible
```

For example:

```java
// Factory
PaymentProcessor processor =
        PaymentFactory.create("UPI");
```

vs.

```java
// Adapter
PaymentProcessor processor =
        new PaymentAdapter(oldGateway);
```

# 8. Real Spring Boot Connection ⭐⭐⭐

Adapters are very common when integrating **external APIs**.

For example, your application defines:

```java
interface NotificationService {
    void send(String message);
}
```

But an external SMS provider gives you:

```java
class ThirdPartySmsClient {

    void sendSms(String text) {
        // external API
    }
}
```

You can create:

```java
@Component
class SmsAdapter implements NotificationService {

    private final ThirdPartySmsClient client;

    public SmsAdapter(ThirdPartySmsClient client) {
        this.client = client;
    }

    @Override
    public void send(String message) {
        client.sendSms(message);
    }
}
```

Your business code only knows:

```java
NotificationService
```

It doesn't need to know the third-party API's method names or implementation details.

This is especially useful for **legacy systems, third-party SDKs, external APIs, payment gateways, SMS providers, cloud SDKs**, etc.

---

# Interview Answer

> **Adapter Pattern is a structural design pattern that allows incompatible interfaces to work together by wrapping an existing class and translating the expected interface into the interface provided by that class.**

### Remember

```text
Existing incompatible class
          ↓
       Adapter
          ↓
Application's expected interface
```

**Factory → Create**
**Builder → Construct**
**Strategy → Choose behavior**
**Observer → Notify subscribers**
**Adapter → Make incompatible interfaces compatible**
