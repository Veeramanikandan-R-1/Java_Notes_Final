# Design Pattern: Observer

**Observer Pattern** is a **Behavioral Design Pattern**.

It is used when **one object's state changes and multiple other objects need to be notified automatically**.

### Simple real-world example

Think about a **YouTube channel**:

```text
                YouTube Channel
                 (Subject)
                      │
            new video uploaded
                      ↓
          ┌───────────┼───────────┐
          ↓           ↓           ↓
      User A       User B       User C
     (Observer)   (Observer)   (Observer)
          ↑           ↑           ↑
       notified     notified    notified
```

The channel doesn't need to manually know the details of each subscriber. It simply **notifies all observers**.

---

# 1. Main Components

There are usually 4 important parts:

```text
Subject
  ├── maintains observers
  ├── subscribe()
  ├── unsubscribe()
  └── notifyObservers()

Observer
  └── update()

ConcreteSubject
  └── actual state

ConcreteObserver
  └── reacts to state changes
```

---

# 2. Complete Working Example

Let's create a **Weather Station**.

When temperature changes, all registered displays should be notified.

### Observer interface

```java
interface Observer {

    void update(double temperature);
}
```

Every observer must implement `update()`.

---

### Subject

```java
import java.util.ArrayList;
import java.util.List;

interface Subject {

    void subscribe(Observer observer);

    void unsubscribe(Observer observer);

    void notifyObservers();
}
```

---

### Concrete Subject

```java
class WeatherStation implements Subject {

    private final List<Observer> observers = new ArrayList<>();

    private double temperature;

    @Override
    public void subscribe(Observer observer) {
        observers.add(observer);
    }

    @Override
    public void unsubscribe(Observer observer) {
        observers.remove(observer);
    }

    public void setTemperature(double temperature) {
        this.temperature = temperature;

        // Temperature changed → notify everyone
        notifyObservers();
    }

    @Override
    public void notifyObservers() {
        for (Observer observer : observers) {
            observer.update(temperature);
        }
    }
}
```

---

### Concrete Observers

```java
class PhoneDisplay implements Observer {

    @Override
    public void update(double temperature) {
        System.out.println(
            "Phone Display: Temperature = " + temperature
        );
    }
}
```

```java
class TVDisplay implements Observer {

    @Override
    public void update(double temperature) {
        System.out.println(
            "TV Display: Temperature = " + temperature
        );
    }
}
```

# 3. Complete `Main`

```java
import java.util.ArrayList;
import java.util.List;

interface Observer {
    void update(double temperature);
}

interface Subject {
    void subscribe(Observer observer);

    void unsubscribe(Observer observer);

    void notifyObservers();
}

class WeatherStation implements Subject {

    private final List<Observer> observers = new ArrayList<>();

    private double temperature;

    @Override
    public void subscribe(Observer observer) {
        observers.add(observer);
    }

    @Override
    public void unsubscribe(Observer observer) {
        observers.remove(observer);
    }

    public void setTemperature(double temperature) {
        this.temperature = temperature;
        notifyObservers();
    }

    @Override
    public void notifyObservers() {
        for (Observer observer : observers) {
            observer.update(temperature);
        }
    }
}

class PhoneDisplay implements Observer {

    @Override
    public void update(double temperature) {
        System.out.println(
            "Phone: Temperature = " + temperature
        );
    }
}

class TVDisplay implements Observer {

    @Override
    public void update(double temperature) {
        System.out.println(
            "TV: Temperature = " + temperature
        );
    }
}

public class Main {

    public static void main(String[] args) {

        WeatherStation station = new WeatherStation();

        Observer phone = new PhoneDisplay();
        Observer tv = new TVDisplay();

        // Subscribe
        station.subscribe(phone);
        station.subscribe(tv);

        // Temperature changes
        station.setTemperature(30);

        System.out.println("---");

        station.setTemperature(35);

        // Unsubscribe TV
        station.unsubscribe(tv);

        System.out.println("---");

        station.setTemperature(40);
    }
}
```

### Output

```text
Phone: Temperature = 30.0
TV: Temperature = 30.0
---
Phone: Temperature = 35.0
TV: Temperature = 35.0
---
Phone: Temperature = 40.0
```

Notice the last update:

```text
Phone → notified
TV    → not notified
```

because TV was unsubscribed.

---

Note:

Observer phone = new PhoneDisplay();

why in left side mostly inteface class name is used instead of PhoneDisplay any reason?

Yes — this is a **very important Java concept**, especially for Spring Boot.

```java
Observer phone = new PhoneDisplay();
```

Here:

```text
Observer       PhoneDisplay
   ↑                ↑
interface       implementation
```

The reason we use the **interface on the left side** is to make the code **loosely coupled**.

### 1. What does the left side mean?

```java
Observer phone
```

means:

> `phone` can refer to **any object that implements `Observer`**.

Since `PhoneDisplay` implements `Observer`:

```java
class PhoneDisplay implements Observer {
    ...
}
```

this is valid:

```java
Observer phone = new PhoneDisplay();
```

You could also have:

```java
Observer tv = new TVDisplay();
Observer email = new EmailDisplay();
```

---

### 2. What if we use `PhoneDisplay`?

You can absolutely do this:

```java
PhoneDisplay phone = new PhoneDisplay();
```

This is also correct.

But now `phone` is specifically tied to `PhoneDisplay`.

If later you want:

```java
phone = new TVDisplay(); // ❌
```

you cannot do it because `TVDisplay` is not a `PhoneDisplay`.

Whereas:

```java
Observer phone = new PhoneDisplay();

phone = new TVDisplay(); // ✅
```

works because both implement `Observer`.

---

### 3. Why is this useful?

Imagine:

```java
interface Payment {
    void pay();
}
```

Implementations:

```java
class UPIPayment implements Payment {
    public void pay() {
        System.out.println("UPI");
    }
}

class CardPayment implements Payment {
    public void pay() {
        System.out.println("Card");
    }
}
```

Instead of:

```java
UPIPayment payment = new UPIPayment();
```

we can use:

```java
Payment payment = new UPIPayment();
```

Now:

```java
payment = new CardPayment();
```

is also valid.

The code using `payment` only cares about:

```java
payment.pay();
```

It doesn't care whether it's UPI or Card.

---

## 4. This is called Programming to an Interface ⭐

You'll hear this phrase a lot in Java interviews:

> **Program to an interface, not an implementation.**

Meaning:

```java
Payment payment = new UPIPayment();
```

rather than:

```java
UPIPayment payment = new UPIPayment();
```

The first approach generally gives you **looser coupling and easier substitution/testing**.

---

## 5. But remember one important limitation

When you write:

```java
Observer phone = new PhoneDisplay();
```

you can only directly call methods available in `Observer`.

For example:

```java
phone.update(30); // ✅
```

If `PhoneDisplay` has its own method:

```java
class PhoneDisplay implements Observer {

    public void update(double temperature) {
    }

    public void showBattery() {
    }
}
```

then:

```java
phone.showBattery(); // ❌
```

because the reference type `Observer` doesn't define `showBattery()`.

---

### Simple mental model

```text
Interface reference
       ↓
Can point to
       ↓
Any implementation
```

So:

```java
Observer phone = new PhoneDisplay();
```

means:

> **"I only care that this object behaves like an Observer; I don't care which concrete Observer it is."**

This concept is **extremely important for Spring Boot Dependency Injection**, so make sure you're comfortable with it.

# 4. Understand the Flow ⭐

When you call:

```java
station.setTemperature(30);
```

this happens:

```text
setTemperature(30)
       ↓
temperature = 30
       ↓
notifyObservers()
       ↓
 ┌─────┴─────┐
 ↓           ↓
Phone       TV
 ↓           ↓
update()    update()
```

The **WeatherStation doesn't need to know how Phone or TV handles the notification**.

It only knows:

```java
Observer observer
```

and calls:

```java
observer.update(temperature);
```

This gives us **loose coupling**.

---

# 5. Why do we need the Observer interface?

Without it, you might write:

```java
phone.update();
tv.update();
email.update();
```

The WeatherStation becomes tightly coupled to every notification type.

With an interface:

```java
List<Observer> observers;
```

it doesn't care whether the observer is:

```text
Phone
TV
Email
Mobile App
Logger
```

Any new observer simply implements:

```java
Observer
```

# 6. Real-world Examples

Observer is useful when **one event needs to notify multiple consumers**.

Examples:

```text
Order placed
    ↓
 ┌──────┬───────┬────────┐
 ↓      ↓       ↓        ↓
Email  SMS   Inventory  Analytics
```

Another example:

```text
Stock price changed
       ↓
 ┌─────┼─────┬──────┐
 ↓     ↓     ↓      ↓
UI   Alert  Logger  Analytics
```

Another familiar example from your React background:

```text
State changes
     ↓
Subscribers
     ↓
Components re-render
```

The underlying idea is similar: **a change is published and interested parties react to it**.

# 7. Observer vs Strategy

Important because you just learned Strategy.

### Strategy

You choose **one behavior**:

```text
PaymentService
      ↓
PaymentStrategy
      ↓
UPI / Card / NetBanking
```

> **"Which algorithm should I use?"**

### Observer

One event notifies **multiple observers**:

```text
WeatherStation
      ↓
 ┌────┼────┐
 ↓    ↓    ↓
Phone TV  App
```

> **"Who needs to know that something changed?"**

# 8. Observer in Spring Boot ⭐⭐⭐

This pattern becomes very useful in Spring Boot.

Spring provides event mechanisms such as:

```java
ApplicationEventPublisher
```

and:

```java
@EventListener
```

For example:

```java
@Component
class EmailListener {

    @EventListener
    public void handleOrderCreated(OrderCreatedEvent event) {
        System.out.println("Send email");
    }
}
```

Another listener:

```java
@Component
class InventoryListener {

    @EventListener
    public void handleOrderCreated(OrderCreatedEvent event) {
        System.out.println("Update inventory");
    }
}
```

Then one event:

```text
OrderCreatedEvent
       ↓
 ┌─────┴──────┐
 ↓            ↓
EmailListener InventoryListener
```

This is an **Observer-style event-driven approach** and is something you'll encounter in real Spring Boot applications.

# Interview Answer

> **Observer Pattern is a behavioral design pattern where an object, called the Subject, maintains a list of dependent objects called Observers and automatically notifies them whenever its state changes.**

### Remember this

```text
Observer
   ↓
One Subject
   ↓
Many Observers
   ↓
State/Event changes
   ↓
Notify all subscribed observers
```

**Factory → creates objects**
**Builder → constructs complex objects**
**Strategy → changes behavior/algorithm**
**Observer → notifies interested objects**
